# V4.5 Cache Affinity and Effective TTFT

## Goal

V4.5 closes the gap between a generic reverse proxy and a cache-aware model
gateway. The target is not to fake a fast first byte. The target is to route
large repeated contexts toward paths that have already shown good cache-read
and first-content behavior.

The intended chain remains source-side only:

```text
Client / Claude Code / CherryStudio
-> NewAPI or direct OpenAI-compatible client
-> ZenProxyRS :4000
-> embedded free-model-client-rs kernel
-> selected Webshare node
-> opencode.ai/zen
```

NewAPI and client-side configuration are not part of this fix.

## Why Some Relay Stations Look Faster

Relay logs often show first-frame latency, not necessarily first useful model
content. For stream APIs these are different moments:

- HTTP first byte.
- first SSE frame.
- first non-empty content token.
- first tool call.
- stream completion.

Large-context sub-second first content usually requires an upstream prompt/KV
cache hit, a warm account/session path, and a fast egress node. ZenProxy cannot
force a slow upstream cache read into one second, but it can avoid sending
repeated large contexts through cold or historically slow paths.

## Landed V4.5 Mechanics

### 1. Effective TTFT Telemetry

Audit telemetry must distinguish:

```text
first_chunk_ms          first upstream body chunk seen by ZenProxy
first_content_token_ms  first non-empty assistant text delta
first_tool_call_ms      first streamed tool-call/tool-use signal
stream_complete_ms      full stream completion
```

`ttft_ms` remains backward-compatible and maps to `first_chunk_ms`.

### 2. Cache Affinity Key

Each request gets a lightweight, non-secret affinity key:

```text
model + protocol + client/session bucket + body size bucket
```

The first implementation intentionally avoids hashing full request bodies on
the hot path. It uses existing client/session identifiers plus coarse request
size buckets. Later versions may add stable system/tools prefix hashes if the
runtime data shows enough benefit.

### 3. Affinity Routing

For large streaming requests, dispatch first tries recently successful nodes
for the same affinity key. If the sticky node cannot admit the request, dispatch
falls back to normal sharded selection.

This must never become a hard pin. A bad or busy affinity node must not block
the request.

### 4. Context-Bucket Learning

Node latency must be learned per request size class:

```text
tiny      <128KB request body
small     128KB-256KB
medium    256KB-512KB
large     512KB-1MB
huge      >=1MB
```

Large-context dispatch should score the node by the matching bucket first, then
fall back to global latency when bucket data is missing.

### 5. Node Tiering

Node details should expose enough data to classify operationally:

```text
hot_large_context  strong large-bucket latency/cache history
normal             ordinary traffic
cold_or_slow       suitable for small traffic or probing
bad_for_large      do not prefer for large context
```

The initial implementation exposes bucket stats. Hard tier labels are allowed
only after enough production samples exist.

## Current Limit

The first implementation is in-memory per ZenProxyRS instance. With nginx in
front of three instances, affinity improves repeated requests that land on the
same instance. Cross-instance affinity can be moved to Redis later if production
data shows enough benefit.

## Acceptance

V4.5 is accepted when:

- stream audit records include `first_content_token_ms` and
  `first_tool_call_ms`;
- repeated same-session large requests show a stable `affinity_key`;
- a successful large stream records `affinity_hit` on follow-up requests when
  the preferred node can admit;
- dispatch details expose per-bucket latency stats;
- existing false-dead protections remain intact;
- `cargo fmt --check`, `cargo test --tests`, and `cargo build --release` pass;
- production smoke still returns the two public models and a streaming 200.

## 2026-05-26 Production Verification

Production rollout on `panda` uses the V4.5 release binary with SHA1:

```text
2b11dbb19861b1d0f16597d1841678d4ad3e3173
```

Verified runtime state:

- `zen-proxy-rs@1`, `zen-proxy-rs@2`, and `zen-proxy-rs@3` are active.
- `http://127.0.0.1:4000/v1/models` returns the two public models.
- direct ZenProxy streaming smoke returned HTTP 200.
- `/admin/budget/nodes` exposes `bucket_latency_ms`.
- `/admin/audit/requests` exposes `affinity_key`, `affinity_hit`,
  `affinity_node_id`, `body_size_bucket`, `first_content_token_ms`, and
  `first_tool_call_ms`.

Observed same-path 150KB stream test:

```text
first call:  affinity_hit=false, first_chunk_ms ~= 2332, total_ms ~= 3089
second call: affinity_hit=true,  first_chunk_ms ~= 1088, total_ms ~= 1882
```

This confirms the V4.5 mechanism is working for repeated large requests that
land on the same ZenProxy instance. It does not prove every large prompt will
reach sub-second first content; upstream cache availability and selected proxy
quality still dominate the long-context floor.
