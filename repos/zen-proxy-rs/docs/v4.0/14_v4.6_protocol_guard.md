# V4.6 Protocol Graph Guard and Pair-Aware Compactor

## Goal

V4.6 prevents malformed tool-call history from reaching the DeepSeek upstream
when Hermes, OpenClaw, Claude Code, CherryStudio, OpenAI SDKs, or Anthropic
SDKs call ZenProxy through NewAPI.

The external chain stays unchanged:

```text
Client
-> NewAPI :8081
-> ZenProxyRS :4000
-> embedded free-model-client-rs kernel
-> selected proxy node
-> DeepSeek upstream
```

NewAPI is not modified. Client-side configuration should not need source-side
workarounds.

## Problem

Some client histories contain tool-result messages that are valid enough to be
stored by a client, but invalid for a strict OpenAI-compatible upstream. The
known failure shape is:

```json
{"role":"tool","content":"..."}
```

without the required field:

```json
"tool_call_id": "..."
```

DeepSeek rejects this with a strict request error such as:

```text
messages[N]: missing field tool_call_id
```

Health checks and normal chat do not expose this. It appears in long tool
sessions, subagent history, mixed OpenAI/Anthropic tool records, and compacted
contexts.

## Target Pipeline

The V4 provider must process tool-aware requests in this order:

```text
raw-body quick scan
-> JSON parse
-> protocol guard pre-scan / safe repair
-> pair-aware compactor
-> protocol guard final repair / strict validate
-> model mapping
-> free-model-client-rs typed request
-> upstream
```

This order matters. A pre-scan alone is not enough because compaction can
remove or rewrite messages after the first repair pass.

## Core Concepts

### Protocol Graph

The guard builds a lightweight graph of message structure:

```text
message index
role
assistant tool_call ids
tool result ids
pending pairs
orphan results
orphan assistant calls
content size
repair actions
quality risk
```

The graph stores indexes and short identifiers. It must not clone large tool
outputs or record raw content in telemetry.

### Safe Repair

OpenAI chat repair rules:

- missing `assistant.tool_calls[].id` gets a stable synthetic ID;
- missing `role=tool.tool_call_id` is filled only when a single unconsumed
  preceding tool call is known;
- multi-tool calls may be paired by `index` and request order when counts
  match;
- uncertain or orphan tool results are downgraded into ordinary `user` context;
- orphan assistant tool calls are downgraded into ordinary assistant context
  rather than left pending.

Anthropic messages repair rules:

- missing `tool_use.id` gets a stable synthetic ID;
- missing `tool_result.tool_use_id` is filled only when a single unconsumed
  preceding tool use is known;
- mixed `text + tool_result` blocks are normalized so invalid tool results do
  not remain in protocol form;
- orphan `tool_result` blocks are downgraded into ordinary text blocks.

Synthetic IDs must be stable across retries. They must be derived from small
fields such as message index, tool index, tool name, argument/input length, and
short hashes of argument/input snippets. They must not use randomness.

### Pair-Aware Compaction

Tool interaction history is compacted as a unit:

```text
assistant tool call(s)
+ matching tool result message(s)
= tool interaction unit
```

The compactor may:

- keep the full unit;
- trim large tool-result content while preserving IDs and tool names;
- downgrade an unsafe or incomplete unit into ordinary context summary.

The compactor must not:

- leave a `role=tool` message without a valid preceding call;
- leave an assistant message with unresolved tool calls;
- split a valid tool pair into an invalid half-pair;
- copy large content just to repair metadata.

## Performance Budget

Protocol guard work happens before upstream dispatch, so it directly affects
TTFT. The implementation must preserve a fast path:

```text
No tool markers in raw body:
  skip graph build and repair

Tool markers present:
  scan message structure only
  avoid large content cloning
  repair in place
```

Target overhead:

```text
no-tool request:       P95 < 0.2ms, throughput drop < 1%
100KB tool history:   P95 < 1ms
1MB tool history:     P95 < 5ms
4MB tool history:     P95 < 15ms
8MB tool history:     P95 < 30ms
TTFT increment:       P95 < 10ms for 100KB-1MB tool histories
```

Guard limits:

```text
PROTOCOL_GUARD_MAX_MS=30
PROTOCOL_GUARD_MAX_GRAPH_MESSAGES=2000
PROTOCOL_GUARD_MAX_REPAIR_ACTIONS=200
```

If limits are exceeded, the guard must degrade to safe-only repair or
downgrade uncertain tool results. It must not spend seconds trying to recover a
broken history.

## Configuration

Recommended defaults:

```text
PROTOCOL_GUARD_MODE=repair
PROTOCOL_GUARD_ORPHAN_POLICY=downgrade
PROTOCOL_GUARD_SYNTHETIC_IDS=true
PROTOCOL_GUARD_LOG_SAMPLE_RATE=1.0
PROTOCOL_GUARD_MAX_MS=30
PROTOCOL_GUARD_MAX_GRAPH_MESSAGES=2000
PROTOCOL_GUARD_MAX_REPAIR_ACTIONS=200
```

Modes:

```text
off             disabled
observe         record issues without changing the request
repair          safe repair and orphan downgrade; default
strict          reject invalid structures instead of recovering them
repair_shadow   compute repairs for telemetry but pass the original body
```

`strict` is for canary and test environments. It is not the default production
mode because old client histories may contain orphan tool results that can only
be recovered as ordinary context.

## Acceptance

V4.6 is accepted when:

- OpenAI `role=tool` without `tool_call_id` no longer reaches DeepSeek;
- missing assistant tool-call IDs are repaired or safely downgraded;
- Anthropic `tool_result` without `tool_use_id` is repaired or safely
  downgraded;
- compaction never creates an orphan tool result or orphan assistant tool call;
- final validation runs after compaction and before typed kernel conversion;
- Hermes/OpenClaw style samples no longer fail with strict upstream
  `tool_call_id` errors;
- mock strict DeepSeek rejects are prevented in the ZenProxy ->
  free-model-client-rs path;
- no-tool request fast path remains measurable and effectively unchanged;
- 1MB, 4MB, and 8MB tool-history guard overhead stays within the target budget;
- all repair/downgrade decisions are visible by request id in audit telemetry.

## Known Limit

If a client history contains only an isolated tool result and the original tool
call is gone, ZenProxy cannot recover the true semantic pairing. The correct
behavior is to downgrade that result into ordinary context so the session can
continue without a 400.

## 2026-05-26 Kernel Canonicalizer Follow-Up

Production Hermes-style traffic exposed a second failure boundary after the
original V4.6 deploy:

```text
protocol=anthropic_messages
path=messages
protocol_guard.post_valid=true
upstream DeepSeek 400: messages[N]: missing field `tool_call_id`
```

Root cause:

- ZenProxy's raw Anthropic guard validates the client-facing `/v1/messages`
  body.
- `free-model-client-rs` then translates Anthropic history into OpenAI chat
  messages for the DeepSeek-compatible upstream.
- A malformed or incomplete Anthropic `tool_result` can become an OpenAI
  `role=tool` message without `tool_call_id` after that translation step.
- Therefore an ingress-only guard is not sufficient. The embedded kernel must
  run a final OpenAI tool-history canonicalizer after Anthropic-to-OpenAI
  translation and before upstream dispatch.

The source-side fix now lives in `free-model-client-rs`:

- OpenAI direct requests are canonicalized before upstream dispatch.
- Anthropic requests are canonicalized after translation into OpenAI messages.
- missing assistant tool-call IDs get deterministic synthetic IDs.
- missing or mismatched tool-result IDs are repaired when a pending call can be
  matched by order.
- orphan tool results are downgraded to ordinary user context.
- unresolved assistant tool calls are downgraded to ordinary assistant context.

This keeps the intended external chain unchanged:

```text
client -> NewAPI -> ZenProxyRS -> embedded free-model-client-rs -> DeepSeek
```

No NewAPI or client-side workaround is required.
