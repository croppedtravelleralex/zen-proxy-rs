## E01 调度池空返回 -999

### 接口层

```
PoolManager.dispatch() 返回 DispatchError::NoResource
-> proxy_handler 收到后返回 HTTP 503
  {"error": {"code": -999, "message": "没有资源可用"}}
```

### 实现层

```
触发条件：DispatchPool.acquire() 遍历所有节点后返回 None

触发场景：
  - 所有 100 个节点同时进 429 池（从未发生，但要保护）
  - 所有节点同时进死池（WebShare 账户整体被封）
  - 熔断开关打开

恢复：
  - 无需手动恢复
  - 节点从 429池/死池 探活成功后自动回到调度池，dispatch() 自动恢复
  - 熔断时需 POST /admin/fuse 关闭熔断
```

### 改动范围

```
  pool/manager.rs  — dispatch() + 5 行判断
  proxy.rs         — Err(NoResource) 分支处理
```

## E02 手动熔断开关 /admin/fuse

### 接口层

```
POST /admin/fuse
  Header: x-api-key: xxx
  Body: {"action": "on"}    -> 所有节点移入死池，返回 -999
  Body: {"action": "off"}   -> 所有节点恢复到调度池

返回: {"status": "ok", "fuse": true|false}
```

### 实现层

```rust
struct PoolManagerImpl {
    fuse: AtomicBool,
}

fn fuse_all(&self) {
    self.fuse.store(true, Ordering::Release);
    // 将调度池和429池所有节点移入死池
}

fn unfuse_all(&self) {
    self.fuse.store(false, Ordering::Release);
    // 将所有节点恢复到调度池，健康度=50
    // 429池和死池清空
}
```

### 改动范围

```
  pool/manager.rs  — fuse_all() + unfuse_all()
  server.rs        — POST /admin/fuse 路由
```

## E03 加权随机选人非绝对最高分

### 接口层

```
DispatchPool.acquire() 用加权随机，不是取最高分
```

### 实现层

```
选人算法：
  total = 所有可用节点的 final_score 之和
  pick = random(0, total)
  cumulative = 0
  for node in nodes:
      cumulative += node.final_score
      if pick <= cumulative: return node

效果：
  - 高分节点被选中概率更高
  - 低分节点偶尔也能被选中
  - 低分节点如果其实恢复了，会被成功抬高分
  - 避免数据偏斜（高分永远高分，低分永远没机会）

final_score 公式 (内部归一化到 0~1, 对外展示时 x100):
  值域: 0.0 ~ 1.0 (监控面板展示 x100 为 0~100)

  health   = base_score / 100.0         健康度 (0~100 -> 0~1)
  success  = recent_success_rate        最近成功率 (0~1)
  idle     = idle_factor()              空闲加分 (0~1)
  latency  = latency_factor()           低延迟加分 (0~1)
  momentum = momentum_factor()          连续成功势头 (0~1)

  final    = health × 0.50
           + success / 0.5 × 0.20       (成功率归一化到 0~0.5 × 0.20 = 0~0.10)
           + idle × 0.15
           + latency × 0.10
           + momentum × 0.05
           ─────────────────────────────────
           范围 0.0 ~ 1.0, clamp(0, 1)
```

### 改动范围

```
  pool/dispatch.rs  — score() + acquire()
```

## E04 动态 max_concurrent 并发控制

### 接口层

```
ActivePool 每个节点维护 max_concurrent
请求到达时 active_requests + 1
请求结束时 active_requests - 1
当 active_requests >= max_concurrent 时，PoolManager 不再从该节点发新请求
```

### 实现层

```rust
初始值: max_concurrent = 5

每次请求成功: max_concurrent = min(max_concurrent + 1, 20)
每次请求失败: max_concurrent = max(max_concurrent / 2, 1)

原理：
  - 成功=上游吃得住->允许更多并发
  - 失败=上游吃不住了->砍半保护
  - 最坏情况降到 1 保底
```

### 改动范围

```
  pool/active.rs    — ActiveEntry.max_concurrent
  pool/manager.rs   — dispatch() 检查 max_concurrent
```

## E05 探活走真实 HTTP 请求

### 接口层

```
所有探活（429池探活、死池探活、探活期探测）都用真实 HTTP 请求：
  POST https://opencode.ai/zen/v1/chat/completions
  Body: {"model":"big-pickle","messages":[{"role":"user","content":"hi"}],"stream":false}
  
  返回 200 -> 节点存活
  返回 429 -> 节点被限流（429池探活继续关着，死池探活也算失败）
  其他失败 -> 节点不存活
```

### 实现层

```rust
async fn probe_node(node_url: &str, creds: &str) -> ProbeResult {
    let client = reqwest::Client::builder()
        .proxy(Proxy::all(node_url))
        .connect_timeout(Duration::from_secs(10))
        .timeout(Duration::from_secs(30))
        .build()?;

    let resp = client
        .post("https://opencode.ai/zen/v1/chat/completions")
        .header("Content-Type", "application/json")
        .header("x-api-key", "public")
        .body(r#"{"model":"big-pickle","messages":[{"role":"user","content":"hi"}],"stream":false}"#)
        .send()
        .await?;

    match resp.status().as_u16() {
        200 => ProbeResult::Alive,
        429 => ProbeResult::RateLimited,  // 对429池，这不算恢复
        _ => ProbeResult::Dead,
    }
}
```

### 改动范围

```
  pool/probe_period.rs  — probe_node()
  pool/ratelimited.rs   — select_for_probe() + 探活循环
  pool/dead.rs          — select_all_for_probe() + 探活循环
```

## E06 429池分批随机探活

### 接口层

```
RateLimitedPool.select_for_probe(batch_size) -> Vec<NodeId>
  从 today 之前的隔离节点中随机抽 batch_size 个
```

### 实现层

```
启动条件：每天早上 8:00
执行周期：每 2~4 小时随机（避免固定节奏被上游识别）
每批数量：3~5 个（控制探活流量）
探活方法：真实 HTTP 请求（E05）

恢复条件：
  - 探活成功(200) -> 回调度池，健康度=50
  - 探活失败(429) -> 留池，consecutive_days++

停止条件：
  - 当天429池为空 -> 停止，等明天
  - 当天再次被429的节点不探活
```

### 改动范围

```
  pool/ratelimited.rs  — select_for_probe() + recover() + 探活循环
  main.rs              — tokio::spawn(ratelimited_probe_loop)
```

## E07 网络波动保护 5分钟观察期

### 接口层

```
探活期结果判定：
  3轮中有 ≥1 成功 -> 不是死，是网络波动
  -> 等待 5 分钟，没有新失败 -> 回调度池
  -> 5 分钟内又失败 -> 重新 3 轮探测
```

### 实现层

```rust
async fn probe_period(node_id, dispatch, dead, collector) {
    let successes = probe_3_rounds(&node_id).await;

    if successes >= 1 {
        // 网络波动，等5分钟
        tokio::time::sleep(Duration::from_secs(300)).await;

        // 再测一次
        if !probe_node(&node_id).await {
            // 又失败了，重新探测
            return probe_period(node_id, dispatch, dead, collector).await;
        }

        // 恢复了
        dispatch.add(NodeRef { id: node_id });
        collector.record_probe(ProbeEvent::recovered(&node_id));
    } else {
        // 3轮全败->死池
        dead.bury(node_id);
        collector.record_probe(ProbeEvent::died(&node_id));
    }
}
```

### 改动范围

```
  pool/probe_period.rs  — 完整函数
```

## E09 统一数据采集层 22字段全量采集 + 3API覆盖

### 接口层

```
trait DataCollector {
  fn record_request(&self, tele: &RequestTelemetry);   // 22字段
  fn record_pool(&self, event: PoolEvent);
  fn record_schedule(&self, event: ScheduleEvent);
  fn record_probe(&self, event: ProbeEvent);
  fn record_system(&self, event: SystemEvent);
  fn snapshot(&self) -> DataSnapshot;
  fn set_backend(&self, backend: Box<dyn StorageBackend>);
}

trait StorageBackend: Send + Sync {
  fn write(&self, snapshot: &DataSnapshot);
  fn name(&self) -> &'static str;

```

### 核心数据模型: RequestTelemetry (22字段)

```
所有字段在 proxy.rs 请求路径上旁路采集, 每请求增加 ~2.5μs 写入成本

┌─────────────────┬──────────┬────────────────────────────────────┐
│ 分类            │ 字段数   │ 举例                               │
├─────────────────┼──────────┼────────────────────────────────────┤
│ 标识            │ 2        │ rid, ts                            │
│ 请求特征        │ 5        │ model, client_id, path, method,    │
│                 │          │ is_streaming                       │
│ 节点/池         │ 3        │ node_url, pool, exit_ip            │
│ 结果            │ 3        │ status, rate_limited, retry_count  │
│ 延迟分解        │ 3        │ latency_total_ms, upstream_ms,     │
│                 │          │ ttft_ms                            │
│ Token           │ 3        │ prompt_tokens, completion_tokens,  │
│                 │          │ total_tokens                       │
│ 带宽            │ 3        │ bytes_sent, bytes_received,        │
│                 │          │ tokens_per_kb                      │
└─────────────────┴──────────┴────────────────────────────────────┘
```

### 三大组件 (新建 collector/ 目录, 5个文件)

```
RingBuffer<RequestTelemetry>
  固定内存 2MB (10k 条), 零分配
  写入: memcpy 到预分配槽位, ~0.3μs
  查询: 从头到尾扫描匹配 filter, 10k 条 ~2ms
  WAL: BufWriter 追加写, 后台每 100ms 批量 fsync, 崩溃最多丢 ~180 条

RollingAggregator
  每 5 分钟封存一个窗口, 保留最近 1h (12个窗口)
  5 个预计算一维 HashMap (model/node/pool/client/status)
  聚合查询 O(1), 多维组合走 RingBuffer 扫描回退
  每 5 分钟写快照到 /tmp/zen-aggregator-snapshot.json

WAL (Write-Ahead Log)
  文件: telemetry.wal (活跃) + telemetry.archive/ (归档)
  策略: 追加写, 每 5min 滚动归档, 保留 24h
  启动回放: 读取 telemetry.wal -> 填充 RingBuffer (<100ms)
```

### 三个 API 端点

```
GET /admin/requests        通用查询 (消费层 + 排查层)
  - 原始明细: ?since=5m&status=429&limit=50
  - 聚合统计: ?since=24h&group=model&aggregate=tokens

GET /admin/events          节点事件流 (运维层)
  - ?node=socks5://...&event=demoted&since=24h

GET /metrics               Prometheus 标签化指标 (取代旧16个裸计数器)
  - ~50 个 metric families, 按 model/status/pool 打标签
  - 新增: zen_proxy_tokens_total, zen_proxy_node_concurrent,
           zen_proxy_active_pool_size 等
```

### 崩溃恢复流程

```
main.rs 启动:
  1. WAL.refill_ring_buffer(&ring_buffer)   回放 ~2MB JSONL, <100ms
  2. RollingAggregator.load_snapshot()      加载快照, <50ms
  3. WAL.purge_old()                        清理超 24h 归档

结果: 崩溃最多丢 ~180 条请求数据 (100ms 批量 fsync 窗口)
```

### 性能预算

```
每请求写入成本: ~2.5μs (RingBuffer ~0.3μs + Aggregator ~1.5μs + WAL ~0.5μs + 计数器 ~0.2μs)
30Mbps 极限 1800 req/s: ~4.5ms/s CPU (0.45%)
内存: ~2.3MB (环形 2MB + 聚合器 0.2MB + 其他 0.1MB)
磁盘: WAL 按 100 req/s 典型值估算:
  100 req/s x 200 bytes x 86400s = ~1.7 GB/天 (未压缩)
  gzip 归档 (5:1) 后 ~350 MB/天
  保留 24h 归档需要 ~700 MB 磁盘
  30Mbps 极限 1800 req/s 时: ~31 GB/天 未压缩, ~6.2 GB 压缩
  建议: 归档保留 4h (极限) / 24h (典型), 超出自动清理
```


## E11 预热池 保持 SOCKS5 连接活跃

### 接口层

```
预热池（WarmPool）—— 不是独立池，是 DispatchPool 的一个内部机制。
每隔 10 秒从调度池选 2~3 个节点，提前建好 SOCKS5 连接。
请求到达时直接复用，不需要现场创建连接，省 200~500ms。
```

### 实现层

```rust
impl<P: NodeProvider> DispatchPool<P> {
    // 后台预热任务
    async fn warm_loop(&self) {
        loop {
            tokio::time::sleep(Duration::from_secs(10)).await;

            // 选 2~3 个最高分但未预热的节点
            let to_warm = self.select_for_warm(3);
            for node in to_warm {
                // 提前建 SOCKS5 连接
                if let Err(e) = self.build_client(&node).await {
                    warn!("warm failed for {:?}: {}", node.id, e);
                }
            }
        }
    }
}
```

### 改动范围

```
  pool/dispatch.rs  — warm_loop() + session_cache 预热逻辑
  main.rs           — tokio::spawn(dispatch.warm_loop())
```

## E12 熔断自动恢复 定期检测上游状态

### 接口层

```
熔断开启后，后台定时检测上游是否恢复。
检测方式：走直连（不使用任何代理节点）发一个请求到上游。
上游返回 200 -> 自动关闭熔断。
```

### 实现层

```rust
impl<P: PoolManager> P {
    async fn auto_unfuse_loop(&self) {
        loop {
            tokio::time::sleep(Duration::from_secs(60)).await;
            if !self.is_fused() { continue; }

            // 走直连测试上游
            let ok = probe_direct().await;
            if ok {
                info!("upstream recovered, auto unfusing");
                self.unfuse_all();
            }
        }
    }
}
```

### 改动范围

```
  pool/manager.rs  — auto_unfuse_loop()
  main.rs          — tokio::spawn
```
