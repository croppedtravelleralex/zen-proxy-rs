# V4.109 Dynamic Free-Model Promotion Goal

## Final Goal

V4.109 turns V4.108's admin-only dynamic model discovery into a controlled
free-model lifecycle system.

The target behavior is:

```text
opencode /zen/v1/models
-> ZenProxy discovery worker
-> candidate registry
-> bounded model probes
-> canary model registry
-> active public model registry for the test channel
-> optional production promotion after explicit approval
```

V4.109 must let newly supported free models be discovered, probed, exposed, and
retired without modifying NewAPI, ClaudeCode, cc-switch, or the production
channel 69. The existing stable public aliases remain mandatory:

```text
deepseek-v4-flash      -> deepseek-v4-flash-free
deepseek-v4-flash-lite -> big-pickle
```

The first production rule is negative: unknown models must never become
production-public just because the provider listed them. For this user's
private self-use test channel, candidates may be listed directly because end
users cannot choose them; this requires
`DYNAMIC_MODEL_PUBLIC_MODE=candidate_canary_or_active` and does not promote the
candidate or relax later canary/active gates.

## Non-Goals

V4.109 must not:

- change NewAPI source code;
- change ClaudeCode, cc-switch, Hermes, or OpenClaw clients;
- overwrite NewAPI channel 69;
- route production traffic to unprobed models;
- expose paid-looking or unknown models;
- apply ClaudeCode-specific request shaping to every unknown model;
- hide model failures behind generic 502/503 errors;
- use discovery probes aggressively enough to drain proxy or token budgets.

## Architecture Contract

The model subsystem is split into four layers:

```text
DiscoverySource
  fetches raw provider model list

DynamicModelRegistry
  stores discovered, missing, ignored, canary, active, retired, quarantined

ProbeEngine
  validates model behavior through bounded OpenAI/Anthropic, stream/non-stream,
  tool-call, and minimal context probes

EffectiveModelRegistry
  merges static aliases with approved dynamic models for `/v1/models` and
  request resolution
```

The request data plane must depend only on `EffectiveModelRegistry`, not on raw
provider discovery. This keeps routing deterministic and testable.

## Model State Machine

Required states:

```text
ignored
candidate
probe_pending
canary
active
missing
retired
quarantined
```

Required transitions:

```text
provider listed free-looking model -> candidate
candidate selected by probe scheduler -> probe_pending
probe success quorum met -> canary
canary traffic success quorum met -> active
provider list absent for grace window -> missing
missing beyond retirement window -> retired
hard protocol or repeated empty-output failure -> quarantined
manual/admin rollback -> candidate or retired
```

Hard safety rules:

- `ignored`, `probe_pending`, `missing`, `retired`, and `quarantined` are not
  public and not routable.
- `candidate` is public/routable only when
  `DYNAMIC_MODEL_PUBLIC_MODE=candidate_canary_or_active` is explicitly enabled
  for a private self-use/test channel. This is a listing/routing shortcut, not a
  lifecycle promotion.
- `canary` is public only when `DYNAMIC_MODEL_PUBLIC_MODE=canary_or_active`
  and only on the test instance.
- `active` can be public for test instances.
- production promotion requires an explicit deploy step and separate approval.

## Public Model Modes

Add a runtime switch:

```text
DYNAMIC_MODEL_PUBLIC_MODE=static_only|candidate_canary_or_active|canary_or_active|active_only
```

Expected behavior:

```text
static_only:
  /v1/models returns only the two stable aliases.

canary_or_active:
  /v1/models returns stable aliases plus canary and active dynamic models.
  Intended only for NewAPI test channel 82 or a later isolated test channel.

candidate_canary_or_active:
  /v1/models returns stable aliases plus candidate, canary, and active dynamic
  models. This is for a private self-use/test channel where end users cannot
  select the model list directly. It does not change lifecycle state and does
  not promote candidates.
  Accepted aliases: self_use, self_use_candidates, test_channel.

active_only:
  /v1/models returns stable aliases plus active dynamic models.
  Candidate production mode after soak.
```

Default must be `static_only`.

For this user's private self-use dynamic-model channel, the intended test
configuration is now:

```text
DYNAMIC_MODEL_PUBLIC_MODE=candidate_canary_or_active
```

That means candidates are deliberately visible/routable in that isolated
channel. This is still not production promotion and must not be copied onto
production channel 69.

## Probe Requirements

A model can move from `candidate` to `canary` only after all required probes
pass.

Manual single-model probe:

```text
POST /admin/models/{model_id}/probe
```

Rules:

- Requires admin auth.
- Uses the same `ModelProbeEngine` as the background discovery worker.
- Does not require `DYNAMIC_MODEL_PROBE_ENABLED=true`; that flag only controls
  background scheduled probes.
- Requires an explicit adapter:
  - `DYNAMIC_MODEL_PROBE_ADAPTER=harness_all_pass` for synthetic harness tests;
  - `DYNAMIC_MODEL_PROBE_ADAPTER=http_bounded` plus
    `DYNAMIC_MODEL_PROBE_BASE_URL` for real bounded HTTP tests.
- `DYNAMIC_MODEL_PROBE_ADAPTER=disabled` returns a clear 422.
- `http_bounded` without `DYNAMIC_MODEL_PROBE_BASE_URL` returns a clear 422
  and must not mutate candidate state.

Required probe set:

```text
metadata:
  model id is free-looking and not denylisted

openai_nonstream_minimal:
  /v1/chat/completions stream=false returns assistant content

openai_stream_minimal:
  /v1/chat/completions stream=true returns valid SSE and real content

anthropic_nonstream_minimal:
  /v1/messages stream=false returns content

anthropic_stream_minimal:
  /v1/messages stream=true returns valid events and real content

tool_history_minimal:
  accepts repaired OpenAI/Anthropic tool history without missing tool_call_id,
  missing tool_use_id, orphan tool result, or invalid assistant message

empty_output_guard:
  no assistant content/tool-call is retried or classified, not exposed as a
  raw ambiguous 502

format_guard:
  model response must not break OpenAI or Anthropic response schema
```

Optional probes after canary:

```text
claudecode_tool_smoke
medium_context_50k
cache_signal_observation
long_stream_stability
```

Probe scheduler constraints:

```text
max concurrent probe models: 1 by default
max probe requests per interval: configurable, default 20
probe traffic lane: model_probe
probe budget: separate from user lanes
probe timeout: bounded and recorded per probe type
probe failures: never bury proxy nodes unless transport evidence proves node fault
```

## Compatibility Policy

All dynamic models share the existing protocol guard and free-model-client
kernel path, but client-specific compatibility remains profile-gated.

Required profiles:

```text
static_flash:
  deepseek-v4-flash only, ClaudeCode deep compatibility allowed

static_flash_lite:
  deepseek-v4-flash-lite only, Hermes/OpenClaw compatibility allowed

dynamic_generic:
  newly discovered models before model-family confidence is known

dynamic_claudecode_compatible:
  only after ClaudeCode probe data proves tool-call compatibility

dynamic_restricted:
  models that can answer simple chat but fail tools or stream correctness
```

Hard rule:

```text
No dynamic model inherits deepseek-v4-flash ClaudeCode deep adaptation just by
name. It must earn a compatible profile through probes.
```

### Final Target

The final V4.109 target is not "show more models in /v1/models". The target is
a production-grade model lifecycle gate:

```text
1. Discover new opencode/free-provider models without code edits.
2. Classify unknown models as non-public candidates by default.
3. Probe candidates through bounded protocol, stream, non-stream, tool-history,
   empty-output, and compatibility tests.
4. Promote only proven models into test-channel canary.
5. Promote canary models to active only after traffic evidence.
6. Retire or quarantine missing, paid-looking, unstable, or protocol-breaking
   models automatically or by admin action.
7. Keep the two stable aliases unchanged forever unless the user explicitly
   approves a separate breaking migration.
8. Let approved models reuse the stable ZenProxy/free-model-client transport,
   proxy pool, cache observation, error mapping, and ClaudeCode-compatible
   formatting only when their profile proves it.
9. Never require NewAPI, ClaudeCode, cc-switch, Hermes, or OpenClaw code changes.
10. Never alter panda production channel 69 during implementation or test
    deployment.
```

  a candidate can be visible for testing while still using `dynamic_generic`.
- Dynamic models must not inherit `deepseek-v4-flash` ClaudeCode deep shaping,
  Hermes/OpenClaw compatibility shaping, or any client-specific kernel behavior
  only because the request came from that client.

Implemented behavior:

- Added model compatibility profiles to the effective model registry:
  - `static_flash`;
  - `static_flash_lite`;
  - `dynamic_generic`;
  - `dynamic_claudecode_compatible`;
  - `dynamic_restricted`.
- Static model mapping now carries profile information:
  - `deepseek-v4-flash -> deepseek-v4-flash-free`, profile
    `static_flash`;
  - `deepseek-v4-flash-lite -> big-pickle`, profile
    `static_flash_lite`.
- Dynamic models now resolve with `dynamic_generic` by default. Retired or
  quarantined dynamic models report `dynamic_restricted` in admin detail.
- V4 provider profile selection now applies a ZenProxy-side model gate before
  calling the free-model-client kernel:
  - `static_flash` keeps ClaudeCode behavior but blocks Hermes/OpenClaw;
  - `static_flash_lite` keeps Hermes/OpenClaw behavior but blocks ClaudeCode;
  - `dynamic_generic` and `dynamic_restricted` force `ClientProfile::unknown`;
  - `dynamic_claudecode_compatible` is reserved for future earned promotion
    and only allows ClaudeCode.
- `/admin/models` and `/admin/models/{model_id}` now expose `profile`.
- `/v1/models/{model_id}` also includes `profile` for routable models, so a
  private test-channel operator can verify that visible candidates are still
  generic.

- `candidate_canary_or_active` still does not promote candidates and does not
