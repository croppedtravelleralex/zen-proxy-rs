# V4.6 99+ Runtime Policy

## Purpose

This page records the V4.6 source-side runtime policy that targets the 99+
acceptance standard. It is the current maintenance entry for quality policy,
large non-stream protection, lane isolation, and timing telemetry.

The chain remains:

```text
client -> NewAPI -> ZenProxyRS -> embedded free-model-client-rs -> selected proxy node -> upstream
```

NewAPI and client prompt configuration are not part of the fix surface.

## Source-Side Quality Policy

`free-model-client-rs` must preserve user intent:

- ordinary requests do not get `thinking={"type":"disabled"}` by default;
- assistant history does not disable thinking by itself;
- terse prompts such as `1`, `继续`, and `执行` are forwarded unchanged;
- only explicit health probes may short-circuit to `ok`;
- tool-use requests may still disable thinking to improve JSON/tool-call stability.

The reason is practical: the previous default-disabled and short-prompt rewrite
made the model more likely to ignore continuation commands, skip subagent/tool
calls, or answer with generic confirmations.

## NonStream Output Guard

ZenProxy applies this guard before calling the embedded kernel:

```text
stream=false + max_tokens missing:
  set max_tokens=2048

stream=false + max_tokens > 4096:
  cap to 4096

stream=false + prompt >= 50k tokens:
  cap max_tokens to 2048

stream=false + prompt >= 100k tokens:
  cap max_tokens to 1024

stream=false + prompt >= 100k tokens + max_tokens > 4096:
  return 422 and require stream=true or a smaller output cap
```

Anthropic `/v1/messages` keeps the previous compatibility default of
`max_tokens=1024` when the client omits it.

Response headers expose the decision:

```text
x-zen-nonstream-guard-action
x-zen-nonstream-prompt-tokens
x-zen-nonstream-original-max-tokens
x-zen-nonstream-max-tokens
```

The guard is a hard production safety gate. It prevents large non-stream calls
from occupying the normal lane for hundreds of seconds and hiding the real
failure behind opaque 502/504 errors.

## Lane Isolation

V4.6 adds three lanes on top of the existing V4.3 lanes:

```text
short_nonstream
normal_stream
large_context
huge_context
long_nonstream
long_output
tool_heavy
```

Default thresholds:

```text
V46_LONG_NONSTREAM_TOKENS=10000
V46_LONG_OUTPUT_TOKENS=4096
V46_LONG_NONSTREAM_CONCURRENCY=4
V46_LONG_OUTPUT_CONCURRENCY=4
V46_TOOL_HEAVY_CONCURRENCY=16
```

Classification rules:

```text
huge_context:
  body/token thresholds from V4.3/V4.5

large_context:
  body/token thresholds from V4.3/V4.5

tool_heavy:
  tools >= 16 or tool markers >= 12

long_output:
  stream=false and max_tokens >= V46_LONG_OUTPUT_TOKENS

long_nonstream:
  stream=false and estimated prompt tokens >= V46_LONG_NONSTREAM_TOKENS

normal_stream:
  stream=true normal chat/messages

short_nonstream:
  remaining non-stream requests
```

The goal is isolation, not magic throughput. Long non-stream and long-output
requests can still be slow, but they must not starve short requests.

Production note, 2026-06-06:

```text
Observed symptom:
  NewAPI channel 69 logged status_code=503 with "zenproxy lane is saturated".

Observed shape:
  request_path=/v1/chat/completions
  stream=false
  long non-stream completions ran for 50-186s
  completion_tokens often reached 6k-21k

Root cause:
  V43_LANE_WAIT_TIMEOUT_MS=1000 was too aggressive for bursty ClaudeCode
  non-stream long-output traffic. The default long_output concurrency of 4 per
  instance can fill quickly; new requests then waited only one second and were
  rejected before upstream work could drain.

Hotfix on panda:
  V43_LANE_WAIT_TIMEOUT_MS=60000
  V4_RETRY_BUDGET_MS=240000
  V46_LONG_OUTPUT_CONCURRENCY=8
  V46_LONG_NONSTREAM_CONCURRENCY=8
  V46_TOOL_HEAVY_CONCURRENCY=24
  V43_HUGE_CONTEXT_CONCURRENCY=3

Why retry budget changed:
  A follow-up error showed stream=false / max_tokens=64000 requests where the
  first upstream attempt failed after about 88s. With the previous 60s retry
  budget, ZenProxy had no room to dispatch a second node and returned 502.
  The 240s budget is aligned with REQUEST_TIMEOUT_SECS=300 so long-output
  non-stream calls can retry once or twice before failing.

Follow-up:
  src/lanes.rs now logs saturated lane details and returns non-secret response
  fields: lane_name, lane_limit, lane_in_flight, waited_ms, body_mb,
  estimated_tokens, stream, and max_tokens.
```

## Timing Metrics

V4.6 separates these timings:

```text
protocol_first_byte_ms:
  first SSE/body chunk seen by ZenProxy

first_content_token_ms:
  first real non-empty text delta

first_tool_call_ms:
  first real tool-call delta
```

`/admin/requests/timings` exposes averages and recent rows with the full
`timings` object. Reports must not use `protocol_first_byte_ms` as a fake
content TTFT.
