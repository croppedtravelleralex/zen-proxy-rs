# V4.3 Scalable Data Plane

## Goal

V4.3 changes the performance target from "more ZenProxy processes" to a
capacity model that can scale under long streaming, large context, and tool
heavy workloads on small VPS profiles such as 1 vCPU / 2 GB RAM.

The main objective is not short non-stream RPM. Short RPM is only a gateway hot
path proof. The primary workloads are:

- long streaming chat completions;
- 8-32 MB large-context streaming requests;
- 32-64 MB huge-context requests with strict isolation;
- Claude Code / CherryStudio tool-call sessions where many requests belong to
  one development workflow.

## Capacity Formula

Use this formula when estimating real capacity:

```text
effective_rpm =
healthy_nodes
* safe_concurrency_per_node
* 60
/ avg_duration_seconds
* upstream_success_ratio
```

For long streaming traffic, concurrency is the main capacity signal:

```text
stream_rpm = stable_stream_concurrency * 60 / avg_stream_seconds
```

Example:

```text
128 stable streams * 60 / 120 seconds = 64 RPM
```

This can be a healthier system than a short-prompt benchmark reporting 2000 RPM,
because it matches the actual interactive workload.

## 1 vCPU / 2 GB Starting Budget

Default V4.3 lane targets for the current local/VPS class:

```text
short_nonstream: 32
normal_stream: 96
large_context: 16
huge_context: 2
large_context_body_mb: 8
huge_context_body_mb: 32
lane_wait_timeout_ms: 1000
```

Expected practical ranges after the data plane is fully optimized:

| Workload | Stable Concurrency | Equivalent RPM |
|---|---:|---:|
| small/medium long streams | 64-128 | 20-120 |
| 8-16 MB large-context streams | 16-32 | 5-30 |
| 24-32 MB large-context streams | 4-8 | 1-8 |
| 32-64 MB huge-context requests | 1-3 | below 1-3 |
| tool-heavy development sessions | 8-24 sessions | workflow-based |

## Landed Slice: Lane Isolation

V4.3 introduces a process-local lane limiter in `src/lanes.rs`.

Runtime behavior:

- `/admin/*`, `/health`, `/metrics`, and model discovery bypass data-plane lane
  limits.
- `/v1/chat/completions` and `/v1/messages` are classified by body size and
  streaming flag.
- Each response gets an `x-zen-lane` header.
- A lane permit is attached to the response extensions so streaming responses
  hold capacity until the response body is dropped.
- If lanes are disabled, the old `V1_MAX_CONCURRENT_REQUESTS` value is still
  used as the single data-plane limit.

Environment switches:

```text
V43_LANES_ENABLED=false
V43_SHORT_NONSTREAM_CONCURRENCY=32
V43_STREAM_CONCURRENCY=96
V43_LARGE_CONTEXT_CONCURRENCY=16
V43_HUGE_CONTEXT_CONCURRENCY=2
V43_LARGE_CONTEXT_BODY_MB=8
V43_HUGE_CONTEXT_BODY_MB=32
V43_LANE_WAIT_TIMEOUT_MS=1000
```

Runtime inspection:

```text
GET /admin/runtime
```

The response includes `v43_lanes.runtime` with max and in-flight counts for each
lane.

## Still Required For Full V4.3

Lane isolation is the first V4.3 slice. Full V4.3 still requires:

- async event bus for request/audit telemetry so hot requests do not write files;
- safe single-writer request ring or another safe request history structure;
- unified `NodeRegistry` and `TransportRegistry` to remove duplicate client
  ownership;
- sharded ready queues to replace whole-pool scan selection;
- local atomic hot budget with Redis used only for cross-host coordination;
- AIMD per-node concurrency based on success, TTFT, 429, busy, and timeout;
- a release-mode benchmark matrix for 1C2G.

## Acceptance

V4.3 lane slice is accepted when:

- `cargo check` passes;
- `/admin/runtime` exposes lane configuration and runtime counts;
- stream, large-context, and short non-stream requests get distinct
  `x-zen-lane` values;
- saturating one lane does not block admin endpoints;
- a low huge-context limit prevents 32-64 MB requests from overwhelming memory.
