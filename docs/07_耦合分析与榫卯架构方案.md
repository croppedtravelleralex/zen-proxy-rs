## 一、当前架构审计

### 评分: 4/10

```
main.rs
  │
  └──> state.rs (AppState — 上帝对象, 14字段来自9个模块)
          │
          └──> proxy.rs 直接操作 6 个模块的内部方法:
                  state.config.upstream_base           ← 直接读字段
                  state.token_bucket.allow()           ← 直接调内部
                  state.proxy_selector.next()          ← 直接调内部
                  state.session_pool.get_client()      ← 直接调内部
                  state.upstream_health.record()       ← 直接调内部
                  state.metrics.record_*()             ← 直接调内部
                  n.record_success()                   ← 跨模块操作ProxyNode
```

### 耦合症状

| 症状 | 等级 | 说明 |
|------|------|------|
| 上帝对象 AppState | 🔴 高 | 14字段, 每个人都能碰一切 |
| 跨模块操作内部 | 🔴 高 | proxy.rs 直接动 ProxyNode (selector模块私有数据) |
| 字符串耦合 | 🟡 中 | "webshare" 散落 selector.rs/node_db.rs/node_probe.rs 三处 |
| 死代码堆积 | 🟡 中 | PoolSelector/StickySession/ProxyRouter/ModelHealth/Bandwidth, 共~500行 |
| 漏接功能 | 🔴 高 | record_error/record_429 未接进 proxy -> 永不黑名单 |
| 编译未优化 | 🔴 高 | 运行 debug 86MB, 不敢切 Release |

## 三、榫卯架构设计

### 3.1 核心 trait 定义

```rust
// ── 池管理器 ──
pub trait PoolManager: Send + Sync {
    fn dispatch(&self, req: &RequestMeta) -> Result<DispatchResult, DispatchError>;
    fn report(&self, node_id: NodeId, result: ResultKind, latency_us: u64);
    fn pool_stats(&self) -> PoolStats;
    fn fuse_all(&self);
    fn unfuse_all(&self);
}

// ── 通用池 ──
pub trait Pool: Send + Sync {
    type NodeId: Clone + Hash + Eq;
    fn acquire(&self) -> Option<NodeRef>;
    fn release(&self, node: &NodeId, result: &ResultKind);
    fn remove(&self, node_id: &NodeId);
    fn add(&self, node: NodeRef);
    fn available(&self) -> usize;
    fn name(&self) -> &'static str;
}

// ── 429池额外能力 ──
pub trait RateLimitedPool: Pool {
    fn quarantine(&self, node_id: NodeId);
    fn select_for_probe(&self, batch_size: usize) -> Vec<NodeId>;
    fn recover(&self, node_id: &NodeId);
    fn quarantined_today(&self) -> usize;
}

// ── 死池额外能力 ──
pub trait DeadPool: Pool {
    fn bury(&self, node_id: NodeId);
    fn select_all_for_probe(&self) -> Vec<NodeId>;
    fn recover(&self, node_id: &NodeId);
    fn dead_count(&self, node_id: &NodeId) -> u32;
}

// ── 数据采集器 ──
pub trait DataCollector: Send + Sync {
    fn record_request(&self, tele: &RequestTelemetry);
    fn record_pool(&self, event: PoolEvent);
    fn record_schedule(&self, event: ScheduleEvent);
    fn record_probe(&self, event: ProbeEvent);
    fn record_system(&self, event: SystemEvent);
    fn snapshot(&self) -> DataSnapshot;
    fn set_backend(&self, backend: Box<dyn StorageBackend>);
}

// ── 存储后端 ──
pub trait StorageBackend: Send + Sync {
    fn write(&self, snapshot: &DataSnapshot);
    fn name(&self) -> &'static str;
}

// ── 节点提供商 ──
pub trait NodeProvider: Send + Sync {
    type NodeId: Clone + Hash + Eq + Debug;
    fn all_urls(&self) -> Vec<String>;
    fn id_for_url(&self, url: &str) -> Self::NodeId;
    fn name(&self) -> &'static str;
}
```

### 3.2 六态五池 + 数据采集器

```
总池 (Warehouse) — 磁盘上的 100 个节点 JSON
     │ 初始化全部进
     ▼
Dispatcher 调度池 — 加权随机选人, 5维度评分
     │ acquire()
     ▼
Active 使用池 — 引用计数, 动态 max_concurrent
     │ 发请求 -> 等结果
     │
     ├── Success -> 留在使用池, 健康度+3
     │
     ├── 429 -> 移入 RateLimited 429池
     │   └── 当天不碰, 次日起每2~4h随机分批3~5个真实请求探活
     │       ├── 成功 -> 回调度池 (健康度=50)
     │       └── 失败 -> 留池
     │
     └── 非429错误 -> 进入 ProbePeriod 探活期 (tokio异步)
             │ 3轮真实请求探测 (间隔500ms)
             ├── 有成功 -> 网络波动 -> 5分钟观察
             │   ├── 无新失败 -> 回调度池 (健康度×0.8)
             │   └── 又失败 -> 重新探活期 (递归)
             └── 全败 -> 移入 Dead 死池
                     └── 每天8:00 真实请求探活
                         ├── 成功 -> 回调度池 (健康度=20)
                         └── 失败 -> dead_count++; dead_count > 30 -> 告警

DataCollector 收集器 (贯穿全程, 5层指标收口)
```

## 四、数据采集层

### 4.1 5层指标总览

```
第1层 — Request (请求层, 9个指标)
  ├── total_requests       总请求数
  ├── success_count        成功数 (200)
  ├── count_429            429数
  ├── count_4xx            4xx数 (不含429)
  ├── count_5xx            5xx数
  ├── timeout_count        超时数
  ├── bytes_sent/bytes_received  字节数
  ├── rpm                  每分钟请求数 (滑动窗口 4096条)
  └── avg_latency          平均延迟

第2层 — Pool (池层, 6个指标)
  ├── dispatch_size        调度池当前大小
  ├── active_size          使用池当前大小
  ├── ratelimited_size     429池当前大小
  ├── dead_size            死池当前大小
  ├── pool_transitions     池间节点转移次数
  └── active_concurrency   当前活跃并发请求数

第3层 — Schedule (调度层, 4个指标)
  ├── acquire_total        调度次数
  ├── no_resource_count   -999触发次数
  ├── avg_score            调度池节点平均评分
  └── score_distribution   评分分布直方图

第4层 — Probe (探活层, 5个指标)
  ├── probe_attempts       探活总次数
  ├── probe_successes      探活成功数
  ├── probe_failures       探活失败数
  ├── probe_avg_latency    探活平均延迟
  └── recovery_rate        探活恢复率 (success / total)

第5层 — System (系统层, 4个指标)
  ├── current_bps          当前带宽 (byte/s)
  ├── memory_bytes         进程内存 (需读取 /proc/self/status)
  ├── uptime_secs          运行时长
  └── task_count           tokio 任务数
```

### 4.3 实现方案

```rust
pub struct DefaultCollector {
    // 请求层: 全部原子计数器
    total_requests: AtomicU64,
    success_count: AtomicU64,
    count_429: AtomicU64,
    count_4xx: AtomicU64,
    count_5xx: AtomicU64,
    timeout_count: AtomicU64,
    bytes_sent: AtomicU64,
    bytes_received: AtomicU64,
    rpm_window: Mutex<VecDeque<Instant>>,
    latency_sum: AtomicU64,
    latency_count: AtomicU64,

    // 池层: RwLock 保护（更新频率远低于读）
    pool_sizes: RwLock<PoolDimensionStats>,

    // 系统层
    bandwidth_bytes: AtomicU64,
    bandwidth_prev: AtomicU64,
    bandwidth_ts: AtomicU64,

    // 后端
    backend: RwLock<Box<dyn StorageBackend>>,
}

impl DataCollector for DefaultCollector {
    fn record_request(&self, tele: &RequestTelemetry) {
        self.total_requests.fetch_add(1, Ordering::Relaxed);
        match tele.status_code {
            200 => { self.success_count.fetch_add(1, Ordering::Relaxed); }
            429 => { self.count_429.fetch_add(1, Ordering::Relaxed); }
            400..=499 => { self.count_4xx.fetch_add(1, Ordering::Relaxed); }
            500..=599 => { self.count_5xx.fetch_add(1, Ordering::Relaxed); }
            _ => {}
        }
        self.bytes_received.fetch_add(tele.body_bytes, Ordering::Relaxed);
        self.latency_sum.fetch_add(tele.latency_us, Ordering::Relaxed);
        self.latency_count.fetch_add(1, Ordering::Relaxed);

        // RPM 滑动窗口
        let mut window = self.rpm_window.lock().unwrap();
        window.push_back(Instant::now());
        while window.len() > 4096 { window.pop_front(); }
    }
}
```

## 五、节点生命周期

```
总池 (100 nodes)
 │ 初始化全进调度池, 健康度=60
 ▼
Dispatch 调度池
 │ acquire() — 加权随机选
 ▼
Active 使用池
 │ active_requests+1 -> 发请求 -> 等结果
 │
 ├── 成功(200)
 │   ├── active_requests-1
 │   ├── 健康度+3 (上限100)
 │   ├── 连续成功+1
 │   ├── max_concurrent+1 (上限20)
 │   └── 留在使用池, 可被再次调度
 │
 ├── 限流(429)
 │   ├── 立即从使用池移出
 │   ├── 健康度=0
 │   └── 进 RateLimited 429池
 │       ├── 当天: 不做任何操作
 │       └── 次日起: 每2~4h分批抽3~5个, 真实请求探活
 │           ├── 200 -> 回调度池 (健康度=50)
 │           └── 429 -> 留池
 │           └── 连续30天429 -> 告警
 │
 └── 非429失败 (502/超时/断连/SSL错)
     ├── 立即从使用池移出
     ├── 连续成功=0
     ├── max_concurrent/=2 (下限1)
     └── 进入 ProbePeriod 探活期 (tokio异步)
         └── 3轮真实请求探测, 间隔500ms
             ├── ≥1轮成功 -> 网络波动
             │   ├── 5分钟无新失败 -> 回调度池 (健康度×0.8)
             │   └── 5分钟内又败 -> 重新探活期
             └── 3轮全败 -> Dead 死池
                 ├── 每天8:00 真实请求探活
                 │   ├── 200 -> 回调度池 (健康度=20)
                 │   └── 失败 -> dead_count++
                 └── dead_count > 30 -> 通知管理员
```

## 九、关键设计决策记录

| 编号 | 决策 | 选择 | 理由 |
|------|------|------|------|
| D01 | 泛型 vs dyn trait | 泛型 | 零运行时开销, 编译器检查配合度 |
| D02 | 池数量 | 5个 (不含探活期) | 满足所有状态过渡 |
| D03 | 探活期不是独立池 | tokio异步任务 | 瞬态(几秒)不需要持久化 |
| D04 | 调度池选人算法 | 加权随机, 非绝对最高分 | 给低分节点恢复机会 |
| D05 | 429池恢复时间 | 次日起2~4h分批探活 | 避免固定节奏被上游识别 |
| D06 | 死池告警阈值 | dead_count > 30 | ~1个月连续死亡 |
| D07 | 无单独 TokenBucket | max_concurrent 控制 | 池状态机自己管节奏 |
| D08 | 探活用真实HTTP请求 | 非TCP ping | TCP无法验证SOCKS5 |
| D09 | 数据采集独立trait | 非Metrics嵌入 | 可换后端、可独立测试 |
| D10 | 检测熔断自动恢复 | 走直连检测上游 | 不需要手动干预 |
