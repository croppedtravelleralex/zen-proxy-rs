## 关键事实（修正后）

1. **API key (`x-api-key: public`) 完全无关** — 用户证实 upstream 不校验 key，任意值均可通过
2. **429 确实发生了** — 测试中 initial 请求返回 200，后续请求返回 429
3. **zen-proxy-rs 在收到 429 后**会执行 `report(ResultKind::RateLimited)`，将节点从 `dispatch` 池移除
4. **所有 100 个节点被移除后**，`dispatch()` 返回 `NoResource`，再重试 3 次后返回 503
5. **无背景探活** — `main.rs` 的 background spawn 只做 snapshot，不触发 probe
6. **probe 只在 `Error{}` 分支触发**，`RateLimited` 分支**不触发 probe**

## 429 真正可能的原因（按概率排序）

### 🔴 原因 A（最可能）: Cloudflare WAF / 浏览器挑战

`opencode.ai/zen` 部署在 Cloudflare 之后。

当 100 个 WebShare SOCKS5 出口 IP（来自不同数据中心）在短时间内以**相同请求模式**（相同 model、相同 payload 结构、相同 user-agent、相同 header 布局）连续请求时，Cloudflare 的 WAF 会判定为爬虫/攻击流量，返回：

```
HTTP 429 Too Many Requests
Body: HTML 格式的 Cloudflare Challenge 页面（JS 挑战或 CAPTCHA）
```

**为什么 initial 请求能通？**
- 第一个请求来自单一 IP，模式干净，Cloudflare 放行
- 后续请求来自不同 IP（轮换），但 payload 模式固定、频率高 → WAF 特征命中

**证据：**
- `proxy.rs:165` 发送的 `x-api-key: public` 被用户证实无额度，排除上游应用层 rate limit
- 429 响应 body 如果被捕获（目前未记录 body 内容），大概率是 HTML 而非 JSON
- 这是多出口代理 + Cloudflare 的经典问题

### 🟠 原因 B: WebShare SOCKS5 代理本身限流

WebShare 对免费/低频套餐可能有：
- 每 IP 连接数限制
- 总带宽限制
- 短时间多连接限流

某些代理节点可能返回 429 表示"当前节点过载"。

**为什么不太可能：**
- WebShare 通常返回 `502/503` 而非 `429` 表示节点不可用
- 100 个节点同时被限流的概率较低

### 🟡 原因 C: Probe 请求未携带 API Key

`src/pool/probe_period.rs:31` 中 probe 请求**不发送 `x-api-key`**：

```rust
client.post(&probe_url).json(&body).send()
// 没有 .header("x-api-key", ...)
```

如果 upstream 在缺少 key 时返回 429（而非 401/403），则 probe 本身会持续失败。

**为什么不太可能：**
- 用户证实 key 是随便填的，说明 upstream 不校验 key → 没有 key 应该也不返回 429
- 但 upstream 的具体行为未实际验证（可能没有 key 时返回 403，也可能返回 429）

### 🟢 原因 D: 模型名 `big-pickle` 不合法

`probe_period.rs:19` 硬编码 `model: "big-pickle"`。

如果 `opencode.ai/zen` 对这个模型名返回 429（虽然罕见），则 probe 会全部失败。

**为什么不太可能：**
- 正常的 API 对非法模型返回 400，而非 429

### 🟢 原因 E: 配置或路径错误

`build_upstream_url` 拼出的完整 URL 为：
```
https://opencode.ai/zen/v1/chat/completions
```

如果 `opencode.ai/zen` 不期望 `/v1/` 前缀，或者期望的是其他路径格式，可能触发边缘情况。

**为什么不太可能：**
- 初始请求 200 说明路径本身是通的

### 🟢 原因 F: Content-Type / Header 问题

probe 请求使用 `.json(&body)` 自动设置 `Content-Type: application/json`，但某些 proxy 节点（socks5h://）可能修改或丢弃 header。

## 代码中确认的缺陷

无论 429 的真实原因是什么，以下代码缺陷都会放大问题：

### 缺陷 1: `RateLimited` 分支不触发 probe

`src/pool/manager.rs:135-139`:
```rust
ResultKind::RateLimited => {
    self.ratelimited.quarantine(node_id.clone());
    self.active.release(&node_id, &result);
    self.dispatch.release(&node_id, &result);
    self.dispatch.remove(&node_id);   // ← 从调度池移除
    // ← 没有 spawn probe！节点永远不会回来
}
```

对比 `Error{}` 分支（lines 141-176），后者会 spawn 一个 probe 异步任务来尝试恢复节点。而 `RateLimited` 分支只是移除了节点，没有任何恢复机制。

**后果**：一旦所有节点因 429 被移除，池子永久为空，直到进程重启。

### 缺陷 2: 无背景周期性探活

`main.rs:148-156` 的 background task 只做 snapshot：
```rust
tokio::spawn(async move {
    loop {
        tokio::time::sleep(tokio::time::Duration::from_secs(60)).await;
        let _snap = state.collector.snapshot();   // ← snapshot only
    }
});
```

没有 `ProbePeriod::probe_multiple()` 定期探测 `ratelimited` 和 `dead` 池中的节点是否已恢复。

### 缺陷 3: `ALLOW_DIRECT_FALLBACK=false` 默认关闭

`config.rs:72`: `allow_direct_fallback: load_env_var("ALLOW_DIRECT_FALLBACK", false)`

当 dispatch 池为空时，如果 `allow_direct_fallback=false`，直接返回 503。如果设置为 `true`，可以跳过代理直连 upstream 作为降级通道。

### 缺陷 4: Probe 没有带 API key

`probe_period.rs` 的 probe 请求不发 API key，与真实代理请求行为不一致。probe 能通过的节点，实际代理可能不同（反之亦然）。

### 缺陷 5: 429 body 未记录/未检查

当前代码只检查 `status == 429`，不解析 response body。如果 429 来自 Cloudflare（HTML challenge）还是来自上游（JSON error），完全无法区分，排查困难。

## 我的猜测（修正版）

> 429 最可能来自 **Cloudflare WAF 的多 IP 轮询检测**。100 个不同出口 IP 以相同 pattern 请求同一 endpoint，触发了 Cloudflare 的 bot 检测。

> 这是一个**架构设计问题而非代码 bug** — 使用大量 SOCKS5 轮换 IP 去请求 Cloudflare 保护的端点，必然会触发 WAF。

---

## 解决方案建议

### 短期（配置级）
1. 在 systemd 中设置 `ALLOW_DIRECT_FALLBACK=true`
2. 降低并发、增加请求间隔
3. 在 probe 请求中也带上 `x-api-key`

### 中期（代码级）
1. `RateLimited` 分支也触发异步 probe（参考 `Error{}` 分支）
2. 添加背景周期性探活任务（每 30s 探测 `ratelimited` + `dead` 池）
3. Probe 请求模拟真实请求的 header/key

### 长期（架构级）
1. 减少 proxy 节点数量（10-20 个而非 100 个），降低 WAF 特征
2. 使用常驻 IP（非轮换），建立长期信任
3. 添加响应 body 日志（至少记录前 500 字节）以区分 429 来源
