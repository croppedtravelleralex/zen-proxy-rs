# ZenProxyRS_M v3.4 最优实施路线

## 核心原则

**最优方案不是马上大规模开发，而是：**

1. 先把 ZenProxyRS_M 当成下一代控制面设计
2. 旧系统继续跑
3. 新能力从旁路控制面逐渐接入

### 推荐路线

| 6 | 不急着换掉 pool，先用 RouteManager 包住现有 pool | 渐进替换 |
| 7 | 不急着做 Dashboard，先把 API 契约做稳 | 前端依赖 API |

### ⚠️ 当前已知故障模式：池空→503

上线生产环境的进程已出现此故障（约 8 小时后触发）：

```
PoolManagerImpl::dispatch() → dispatch 池空
  → ALLOW_DIRECT_FALLBACK=false（默认）→ NoResource
  → proxy_with_retry 重试 3 次 → 仍 NoResource
  → 返回 503 upstream error
  → 所有后续请求全部 503，直到进程重启
```

**根因：** 107 个节点全部进了 RateLimited（70） 和 Dead（37） 池。
- RateLimited 分支不触发 probe → 节点进限流池后永不恢复
- 无周期性探活 → Dead 池即使有节点已恢复也没人检查
- ALLOW_DIRECT_FALLBACK 默认 false → 池空时不做直连降级

**v3.4 必须在 Phase 1 彻底解决此故障。详见 [Phase 1 关键 bug 修复](#phase-1-中的关键-bug-修复)。**

产出：
- ✅ v3.4 产品定位（本文档）
- ✅ v3.4 架构目标（分层架构）
- ✅ v3.4 API 契约（Public + Admin）
- ✅ v3.4 数据模型（领域对象）
- ✅ v3.4 迁移计划

## Phase 0.5：请求指纹对齐与 WAF 规避（P0 — 核心代理路径修复）

**目标：修复当前代理路径中的 6 个关键缺陷，使请求指纹与 opencode CLI 对齐，避免被 Cloudflare WAF 标记为爬虫流量。**

### 背景

通过反编译 opencode 源码 + 实际 WSL 抓包验证，确认当前 ZenProxyRS 与 opencode CLI 发送的请求存在 6 个关键差异。这些差异叠加导致 WebShare 100 IP 轮换模式很快触发 Cloudflare WAF：

| 维度 | opencode CLI | ZenProxyRS 当前 | 后果 |
|---|---|---|---|
| x-opencode-* 头 | 全部发送 | 默认关闭 | 指纹不一致（影响 WAF），丢 session 粘滞能力 |
| User-Agent | `opencode/1.3.15` | reqwest 默认 | WAF 指纹不匹配，易被标记 |
| API key 位置 | `Authorization: Bearer public` | `x-api-key: public` | 等效（不影响） |
| IP 数量 | 1 个固定 IP | 100 个 WebShare IP 轮换 | **触发 WAF 多 IP 检测** |
| Probe API key | 发送 | `_api_key` 下划线前缀，不发 | Probe 401 → 节点永不恢复 |
| 重试行为 | 同一节点重试 | 每次选新节点 | 加速池耗尽 |
| PROXY_API_KEY | 自带 | 声明但从不校验 | 无认证 |

### 缺陷 1：100 IP 轮询触发 Cloudflare WAF

**代码证据：** 100 个 WebShare SOCKS5 出口 IP 全部通过 ZenProxyRS 发送到 `opencode.ai/zen/v1/chat/completions`。

**opencode 服务端视角（`ipRateLimiter.ts`）：**
```typescript
// 每个 IP 有自己的计数器
const rows = await tx.select()
  .from(IpRateLimitTable)
  .where(eq(IpRateLimitTable.ip, ip))
```
即使每个 IP 的额度没用完，Cloudflare WAF 会在更上层拦截——它检测到 100 个不同 IP 从同一 Rust 客户端（相同 TLS 指纹、相同 HTTP 框架、相同 body 结构、相同时间窗口）同时请求同一 endpoint，判定为爬虫/代理滥用。

**Clash Verge 为什么能用很久：**
- 1 个固定 IP，请求间隔自然（用户打字/思考的间隙）
- User-Agent 和 headers 与浏览器/CLI 一致
- 没有 100 IP 同时请求的异常模式

**修复方案：粘滞路由 + 并发控制**

```rust
// 新增：并发控制配置
pub struct WafAvoidanceConfig {
    /// 同一 client_id 尽量走同一 node（出口 IP 不变）
    pub sticky_by_client: bool,
    /// 同一 model 尽量走同一 route（避免 100 IP 轮询）
    pub sticky_by_model: bool,
    /// 每个 route 最大并发请求数
    pub max_concurrent_per_route: u32,
    /// 每次切换最多轮换多少节点
    pub max_rotation_count: u32,
}
```

默认值：
- `sticky_by_client: true` —— 同一用户粘滞同一出口 IP
- `sticky_by_model: true` —— 同一模型粘滞同一 route
- `max_concurrent_per_route: 10` —— 单 route 最多 10 并发（而不是 100）
- `max_rotation_count: 3` —— 失败后只换 3 个节点，而非全部轮换

**改造点：`src/pool/dispatch.rs` + `src/pool/manager.rs`**

```rust
// DispatchPool.acquire() — 增加粘滞逻辑
fn acquire(&self, meta: &RequestMeta) -> Result<AcquiredNode> {
    // 1. 优先返回粘滞节点（按 client_id 或 model 缓存）
    if let Some(sticky) = self.try_sticky(meta) {
        return Ok(sticky);
    }
    // 2. 加权评分选节点（现有逻辑）
    let node = self.weighted_select(meta)?;
    // 3. 记录粘滞关系（后续请求优先选同一节点）
    self.record_sticky(meta, &node);
    Ok(node)
}
```

**工作量：** 中（`pool/mod.rs` + `dispatch.rs`，~120 行）
**对核心路径影响：** 新增 HashMap 查询 + 更新，约 1μs

### 缺陷 2：缺少 opencode headers → 指纹不一致

**代码证据：** `src/config.rs:91` —— `opencode_headers_enabled` 默认 `false`。

**opencode 源码确认：** 注意有两个版本——

| 版本 | 源码位置 | headers 对限流的影响 |
|---|---|---|
| sst/opencode `b2baddcd`（当前生产环境的基线） | `ipRateLimiter.ts` 无 `checkHeaders` 逻辑 | **不影响**，headers 仅用于粘滞路由 + 埋点 |
| anomalyco/opencode dev（后来更新） | `ipRateLimiter.ts` 增加了 `checkHeaders` | 影响 —— headers 存在使用标准额度，否则 fallback |

当前 `opencode.ai/zen` 生产环境运行更接近 `b2baddcd` 版本（已验证：不加 headers 仍可正常请求直到额度用完），**headers 不影响 rate limit 额度**。但仍应发送的原因：
1. 模拟真实 CLI 指纹（降低被 WAF 标记的概率）
2. Session ID 用于服务端粘滞路由
3. 为将来版本升级做准备（anomalco 分支已增加 checkHeaders）
4. 指标埋点

**修复方案：默认启用 opencode headers + 指纹注入**

```rust
// config.rs — 修改默认值
opencode_headers_enabled: load_env_var("OPENCODE_HEADERS_ENABLED", true), // false → true
```

并确保所有 opencode 头都有合理默认值：

| 头 | 值 | 来源 |
|---|---|---|
| `User-Agent` | `opencode/{version}` | `opencode_user_agent_version` |
| `x-opencode-client` | `cli` | 固定（模拟 CLI）|
| `x-opencode-project` | 短哈希 | `opencode_project_seed` 衍生 |
| `x-opencode-session` | `{model_hash}-{client_hash}` | `build_session_id()` 不变 |
| `x-opencode-request` | UUID v4 | 每请求新生成（已有逻辑）|

**工作量：** 小（`config.rs` + `proxy.rs`，改 2 行 + 调整顺序 5 行）

### 缺陷 3：Probe 不带 API key

**代码证据：** `src/pool/probe_period.rs` —— 参数名为 `_api_key`（Rust 惯例：下划线前缀表示故意不用）。

```rust
// 当前
pub async fn probe_node(
    url: &str,
    client: &reqwest::Client,
    _api_key: &str,     // ← 下划线前缀：接收但不使用
    model: &str,
) -> bool { ... }

// 实际构建的 probe 请求
let req_body = serde_json::json!({
    "model": model,
    "messages": [{"role": "user", "content": "ping"}]
});
// 注意：没有 Authorization 头，没有 x-api-key 头
```

**后果：**
- probe 请求不带认证 → opencode 返回 401
- probe 失败 → 节点被继续标记为 dead/ratelimited
- 节点永不恢复 → dispatch 池持续减少 → 最终 503

**修复方案：probe 请求也带 API key**

```rust
// probe_period.rs — 修复后
pub async fn probe_node(
    url: &str,
    client: &reqwest::Client,
    api_key: &str,      // ← 去掉下划线，实际使用
    model: &str,
) -> bool {
    let req_body = serde_json::json!({
        "model": model,
        "messages": [{"role": "user", "content": "ping"}]
    });
    let req = client
        .post(url)
        .header("Content-Type", "application/json")
        .header("x-api-key", api_key)   // ← 新增：probe 也带认证
        .json(&req_body);
    // ... 重试逻辑不变 ...
}
```

同时修改调用点——`PoolManagerImpl` 需持有 `upstream_api_key` 引用传给 probe：

```rust
// pool/manager.rs
pub struct PoolManagerImpl<D, A, R, K> {
    upstream_api_key: String,  // 新增字段
    // ...
}

// report() 中调用 probe 时传入
tokio::spawn(async move {
    ProbePeriod::probe_node(&url, &client, &self.upstream_api_key, &model).await;
});
```

**工作量：** 小（`probe_period.rs` + `manager.rs`，改 ~10 行）

### 缺陷 4：每次重试选新节点加速池耗尽

**代码证据：** `src/proxy.rs` `proxy_with_retry` 第 174-187 行

```rust
for attempt in 0..=max {
    // 每次重试都调用 dispatch() → 选新节点
    let dispatch_result = match state.pool_manager.dispatch(req_meta) {
        Ok(r) => r,
        // ...
    };
    // 用新节点发送请求
    let client = dispatch_result.client;
    let mut req = client.request(...);
}
```

**后果：** 如果节点 A 返回 429，重试时选节点 B 去请求同一上游。节点 B 也触发限流，再换节点 C……不是"重试"而是"消耗更多节点"。

**修复方案：重试优先同一节点**

```rust
for attempt in 0..=max {
    // 第 1 次：正常选节点
    // 第 2 次起：优先用上次的节点（如果上次失败不是因为节点本身问题）
    let dispatch_result = if attempt == 0 || last_status == Some(502) {
        // 第一次 或 连接错误（节点确实死了）→ 换节点
        state.pool_manager.dispatch(req_meta)?
    } else {
        // 429/5xx 可能是上游限流，重试同一节点（带上退避）
        state.pool_manager.dispatch_sticky(req_meta, &last_node_id)
            .or_else(|_| state.pool_manager.dispatch(req_meta))?
    };
    // ...
}
```

**新增 `PoolManager` trait 方法：**
```rust
/// 尽量返回指定 node_id，如果该节点不可用则 fallback 到 dispatch
fn dispatch_sticky(&self, meta: &RequestMeta, node_id: &str) -> Result<AcquiredNode, DispatchError>;
```

**工作量：** 中（`pool/mod.rs` trait + `manager.rs` 实现，~30 行）

### 缺陷 5：PROXY_API_KEY 存在但不校验

**代码证据：** `src/proxy.rs:47`

```rust
let client_id = extract_bearer_token(&headers).unwrap_or_default();
// 只用作 telemetry 的 client_id，不做任何认证
```

`src/config.rs` 声明了 `proxy_api_key` 字段，但 proxy_handler 从没调用过：

```rust
proxy_api_key: match env::var("PROXY_API_KEY") {
    Ok(v) if !v.is_empty() => Some(v),
    _ => None,
},
```

**后果：** New-API 可以不带 token 直接调 ZenProxyRS，任何人都能用你的代理。

**修复方案：在 proxy_handler 入口校验 Bearer token**

```rust
// proxy.rs — proxy_handler 顶部
pub async fn proxy_handler(
    State(state): State<Arc<AppState>>,
    method: Method,
    Path(path): Path<String>,
    headers: HeaderMap,
    body: axum::body::Bytes,
) -> Response {
    // 校验 PROXY_API_KEY
    if let Some(ref expected) = state.config.proxy_api_key {
        let bearer = extract_bearer_token(&headers);
        match bearer {
            Some(token) if token == *expected => { /* 通过 */ }
            _ => {
                return (StatusCode::UNAUTHORIZED, Json(serde_json::json!({
                    "error": "unauthorized",
                    "message": "Missing or invalid API key"
                }))).into_response();
            }
        }
    }
    // ... 继续处理请求 ...
}
```

**工作量：** 小（`proxy.rs` 改 ~15 行）

### 缺陷 6：原始请求 headers 不转发

**代码证据：** `src/proxy.rs:197-207`

```rust
let mut req = client.request(req_method, &upstream);
req = req.header("Content-Type", "application/json");
req = req.header("x-api-key", &state.config.upstream_api_key);
// 原始 headers 完全被丢弃
```

**后果：**
- opencode 看不到 New-API 发送的原始 User-Agent、Accept 等头
- 请求指纹与 CLI 不一致
- 丢失客户端传递的自定义头信息

**修复方案：选择性转发原始 headers**

非破坏性原则——只转发安全头，不覆盖已显式设置的头：

```rust
// proxy.rs — proxy_with_retry 请求构造
let mut req = client.request(req_method, &upstream);

// 1. 设置核心头（已有）
req = req.header("Content-Type", "application/json");
req = req.header("x-api-key", &state.config.upstream_api_key);

// 2. 转发原始请求中的安全头（不覆盖已设置的）
const FORWARDED_HEADERS: &[&str] = &[
    "user-agent",
    "accept",
    "accept-encoding",
    "accept-language",
    "cache-control",
];
for name in FORWARDED_HEADERS {
    if let Some(value) = headers.get(*name) {
        // 不覆盖显式设置的值
        if req.headers_ref().and_then(|h| h.get(*name)).is_none() {
            req = req.header(*name, value);
        }
    }
}

// 3. 再追加 opencode 头（已有逻辑）
```

**工作量：** 小（`proxy.rs` 改 ~15 行）

### 核心发现：两个不同版本

| 特性 | sst/opencode b2baddcd | anomalyco/opencode dev（后来版本） |
|---|---|---|
| IP 限流 | 只有 `dailyRequests` | 增加了 `dailyRequestsFallback` + `checkHeaders` |
| opencode headers 的作用 | 仅用于 sticky routing + 埋点 | 影响 rate limit 额度 |
| 源码位置 | `packages/console/app/src/routes/zen/util/` | 同路径 |
| license | SST License | Apache 2.0 |

**当前 opencode.ai/zen 生产环境运行的版本更接近 b2baddcd**，因为：
- 实测不加 opencode headers 也能拿到标准额度（每天都可请求直到 `dailyRequests` 次）
- `retry-after` 返回到午夜 UTC 的秒数，与 b2baddcd 的 `getRetryAfterDay()` 完全一致
- `FreeUsageLimitError` 响应体与 b2baddcd 的 error handler 一致

**结论：对于当前生产环境，opencode headers 不影响 rate limit 额度。** 但是发送仍有益处：支持 session 级别粘滞路由、埋点指标、以及为将来版本升级做准备。

### IP 限流器源码（ipRateLimiter.ts，完整）

```typescript
export function createRateLimiter(modelId, rateLimit, rawIp, request) {
  const limits = Subscription.getFreeLimits()
  const dailyLimit = rateLimit ?? limits.dailyRequests  // 模型可覆盖默认值
  const isDefaultModel = !rateLimit

  const ip = rawIp.length ? rawIp : "unknown"
  const now = Date.now()
  const lifetimeInterval = ""  // 空字符串 = 终身计数器
  const dailyInterval = rateLimit
    ? `${buildYYYYMMDD(now)}${modelId.substring(0, 2)}`  // 有 rateLimit 的模型按模型+日分片
    : buildYYYYMMDD(now)                                  // 默认模型按日分片

  return {
    check: async () => {
      const rows = await db.select()
        .from(IpRateLimitTable)
        .where(and(eq(ip), isDefaultModel
          ? inArray([lifetimeInterval, dailyInterval])
          : inArray([dailyInterval])
        ))
      const lifetimeCount = rows.find(r => r.interval === lifetimeInterval)?.count ?? 0
      const dailyCount = rows.find(r => r.interval === dailyInterval)?.count ?? 0

      // 新 IP 判断：终身请求 < dailyLimit × 7
      _isNew = isDefaultModel && lifetimeCount < dailyLimit * 7

      // 新 IP: dailyLimit × 2, 老 IP: dailyLimit
      if ((_isNew && dailyCount >= dailyLimit * 2)
        || (!_isNew && dailyCount >= dailyLimit))
        throw new FreeUsageLimitError("Rate limit exceeded", getRetryAfterDay(now))
    },
    track: async () => {
      // 后端：写入数据库，计数值 +1
      // 终身计数器仅在 _isNew 期间写入
    },
  }
}

function getRetryAfterDay(now) {
  return Math.ceil((86_400_000 - (now % 86_400_000)) / 1000)
}
```

**要点：**
- **免费模型永远走 IP 限流**，给 API key 也没用（`allowAnonymous = true` 强制走 ipRateLimiter）
- **`dailyRequests` 的具体数值是 SST Secret**，不在开源代码中（环境变量 `ZEN_LIMITS`）
- **新 IP 前 `dailyLimit × 7` 次请求额度翻倍**，之后降到正常
- **retry-after 是服务端本地计算**：到午夜 UTC 的秒数，客户端无法修改
- **不同模型共享同一日额度**（除非模型配置了 `rateLimit` 覆盖）
- **有 `rateLimit` 的模型：按模型+日分片，无终身计数器**

### Trial 限流器源码（trialLimiter.ts）

```typescript
export function createTrialLimiter(trialProviders, ip) {
  if (!trialProviders) return  // 模型没有配置 trialProvider 就不创建
  const limit = Subscription.getFreeLimits().promoTokens

  return {
    check: async () => {
      const data = await db.select({ usage: IpTable.usage })
        .from(IpTable).where(eq(ip, ip))
      _isTrial = (data?.usage ?? 0) < limit
      return _isTrial ? trialProviders : undefined
    },
    track: async (usageInfo) => {
      if (!_isTrial) return
      const usage = inputTokens + outputTokens + reasoningTokens
        + cacheReadTokens + cacheWrite5mTokens + cacheWrite1hTokens
      db.insert(IpTable).values({ ip, usage })
        .onDuplicateKeyUpdate({ set: { usage: usage + new_usage } })
    },
  }
}
```

**要点：**
- **按 IP 累计 token 总量**，所有 token 类型都计入（input/output/reasoning/cache）
- **超过 promoTokens 阈值后**：不再走 trial provider（但仍可正常请求，只是换 provider）
- **promoTokens 也是 SST Secret**，具体数值不在开源代码中
- **与 IP 限流独立**——用完 trial 和用完日额度是两回事

### Provider 选择算法（selectProvider，handler.ts 行 484-577）

```
优先级顺序：
  1. BYOK（用户自配 API key）→ 最高优先级
  2. Sticky provider（本 session 上次用的 provider）→ 通过 stickyProviderTracker
  3. Trial provider（试用期用户）→ 从 trialProviders 随机选
  4. 加权轮询（正常情况）→ 算法如下：
     a. 过滤：disabled=0, weight!=0, 未排除, TPM 未超限
     b. 找最高优先级（priority 最小）
     c. 按 weight 展开为数组（weight=3 → 出现 3 次）
     d. 用 sessionId 末 4 位（或 IP）做确定性哈希选 provider
  5. Fallback provider（重试耗尽后）→ modelInfo.fallbackProvider

上游 429 重试（fetchWith429Retry）：
  - 最多 3 次，指数退避：500ms, 1000ms, 2000ms
  - 重试超限后排除当前 provider 触发 failover（最多 3 次 failover）
```

### 对 ZenProxyRS 设计的指导意义

1. **粘滞路由是唯一有效手段**——IP 日额度是写死的，无法绕过
2. **100 IP 不是优势而是劣势**——每个 IP 的日额度独立，100 IP 轮换只是把 100 份日额度各用一点，不如 1 个 IP 把一份额度用到底再换
3. **重试不换节点是关键**——opencode 服务端自己有 failover 逻辑（3 次 + 500ms/1s/2s 指数退避），如果客户端也换节点，两层的重试叠加会放大问题
4. **Probe 带 API key**——虽然是免费模型注定走 IP 限流，但不带 key 的请求 opencode 会直接 401（faster 拒绝）
5. **Trial limiter 按 token 计量**——短请求（hello）消耗少，长对话消耗快

##### Phase 1a-H：exit_ip 捕获（小）

当前 exit_ip 在 RequestTelemetry 和 LedgerEvent 中均有字段但恒为 None。不依赖 TransportAdapter（Phase 6），直接在 proxy.rs 中从 `reqwest::Response` 的响应头中捕获：

```rust
// 直接从 reqwest::Response headers 中提取
fn capture_exit_ip(response: &reqwest::Response) -> Option<String> {
    response.headers()
        .get("X-Forwarded-For")
        .or_else(|| response.headers().get("X-Real-IP"))
        .or_else(|| response.headers().get("CF-Connecting-IP"))
        .and_then(|v| v.to_str().ok())
        .map(|s| s.to_string())
}
```

**注意：** exit_ip 捕获的效果取决于 upstream 是否在响应头中回传这些信息。opencode 当前版本不确定是否包含。如果 upstream 不传，此字段可能仍为 None——这是上游限制，非代码 bug。

### 配置边界：启动环境变量 vs 运行时 API

| 类型 | 生效方式 | 示例 |
|---|---|---|
| **启动专用**（环境变量） | 进程重启生效 | PORT, BIND_ADDRESS, UPSTREAM_BASE, NODES_FILE, LEDGER_EVENTS_PATH, TELEMETRY_WAL_PATH |

## Phase 3：实现控制 Admin API + 扩展 Fuse

**前提：** Phase 2 完成（只读 API 就绪）。控制端点依赖 Phase 1b 的子池 Arc（dead_pool.bury() 等操作可直接调用）。

### 3a：熔断控制（Fuse 扩展）+ 控制端点

| 路径 | 方法 | 操作 | 延迟 |
|---|---|---|---|
| `POST /admin/fuse` | `AdminService.fuse(open)` | pool_manager.fuse_all/unfuse_all | < 1ms |

### 3b：FuseManager 多 scope 扩展

| 动作 | 工作量 | 说明 |
|---|---|---|
| 定义 FuseManager trait | 小 | 支持 Global/Provider/Node/Route/Model 多 scope |
| 实现 FuseState 存储 | 中 | HashMap<FuseScope, FuseState> |
| 向后兼容 | — | GET /admin/fuse 默认返回 global scope，旧客户端不受影响 |

### 关键设计约束

1. **Probe 必须异步：** `POST /admin/nodes/{id}/probe` 不能直接在 handler 里 `await`。方案：handler 启动 tokio::spawn 返回 `{probe_id: "..."}`，客户端通过 `GET /admin/events/probes?probe_id=` 轮询结果。

2. **Config 写锁：** `POST /admin/config/reload` 持有写锁约 20ms。期间所有读配置的请求路径会短暂阻塞。**高峰期慎用。**

3. **熔断操作的 `dry_run` 支持：** POST /admin/fuse body 支持 `{"open": true, "dry_run": true}`，只返回受影响节点数不改状态。
