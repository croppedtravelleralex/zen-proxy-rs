## 集成测试策略

### 为什么需要集成测试

57 个 Admin API 端点 + 认证中间件 + 控制操作（节点增删、熔断开关）与代理请求并发运行——单元测试覆盖不了这些交互场景。

### 测试方案

使用 `axum::test` 或 `tower::ServiceExt` 在进程内启动完整路由：

```rust
#[tokio::test]
async fn test_admin_api_full_flow() {
    // 1. 用真实 AppState 构建 router
    let app = build_admin_router(test_state());

    // 2. 无认证 → 401
    let resp = app
        .oneshot(Request::builder()
            .uri("/admin/pools")
            .body(Body::empty())
            .unwrap())
        .await.unwrap();
    assert_eq!(resp.status(), 401);

    // 3. 带认证 → 200 + 统一响应格式
    let resp = app
        .oneshot(Request::builder()
            .uri("/admin/pools")
            .header("x-api-key", "test-key")
            .body(Body::empty())
            .unwrap())
        .await.unwrap();
    assert_eq!(resp.status(), 200);
    let body: Value = serde_json::from_slice(&hyper::body::to_bytes(resp.into_body()).await.unwrap()).unwrap();
    assert_eq!(body["success"], true);
}

#[tokio::test]
async fn test_control_api_concurrent() {
    // 测试控制操作 + 代理请求并发时的正确性
    // 例如：POST /admin/nodes/{id}/recover 同时 dispatch() 获取节点
}
```

### 覆盖范围

| 场景 | 测试方式 |
|---|---|
| 全部 57 端点认证 | 自动化，每端点 401/200 对 |
| 控制操作 + 代理并发 | 自动化，tokio::spawn 同时触发 |
| 熔断开关 + 请求路径 | 自动化 |
| 节点增删 + dispatch | 自动化 |
| 配置热加载 + 请求 | 自动化 |
| WAL 写入 + 恢复 | 自动化 |
| 快照导出 | 自动化 |

### 与单元测试的关系

- 单元测试：验证单个模块逻辑正确性（评分算法、状态转换、header 构建）
- 集成测试：验证多个模块组装后的行为正确性（API → Pool → DataCollector 完整链路）
- 两者互补，集成测试不是替代单元测试
