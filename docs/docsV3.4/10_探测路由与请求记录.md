## 1. 探测（Probe）

### 探测类型

| 类型 | 说明 | 当前状态 |
|---|---|---|
| Provider list models | 列出上游 /v1/models | ❌ 不存在 |
| Candidate model sample call | 对候选模型发测试请求 | ❌ 不存在 |
| Node availability | 节点存活探测 | ✅ ProbePeriod::probe_node() |
| Streaming support | 检测模型是否支持流式 | ❌ 不存在 |
| Tool calling probe | 检测 tool calling 支持 | ❌ 不存在 |
| Free-likely probe | 判断模型是否免费 | ❌ 不存在 |
| Latency probe | 测量延迟 | ❌ 不存在 |
| Rate-limit probe | 探测限流阈值 | ❌ 不存在 |

### 当前节点探测

```rust
// pool/probe_period.rs
ProbePeriod::probe_node(url, client) -> bool {
    // 向上游发 POST /v1/chat/completions（模型 big-pickle）
    // 最多 3 次重试，500ms 间隔
    // 任一成功返回 true
}
```

`PoolManagerImpl` 在 `report()` 中当节点失败时触发后台 tokio::spawn 探活。

### 已知缺陷（来自 10_429 根因分析）

1. RateLimited 分支不触发 probe — 节点进入 429 池后永不恢复直到重启
2. 无背景周期性探活 — main.rs 后台任务只做 snapshot，不 probe 隔离池
3. Probe 请求未带 API key — 与真实请求行为不一致
4. retry_after、tokens、exit_ip 字段已声明但尚未从上游响应中捕获

### v3.4 改进：Probe 指纹与真实请求对齐

当前 probe 请求的指纹与真实代理请求差异很大，导致 probe 结果不可靠：

| 维度 | 当前 probe | 真实请求 | v3.4 目标 |
|---|---|---|---|
| API key | 不带 | 带 `x-api-key` | probe 也带 |
| OpenCode headers | 不带 | 注入 5 个 header | probe 可选注入 |
| 模型名 | 硬编码 `big-pickle` | 来自用户请求 | probe 使用真实常用模型 |
| 请求体结构 | 固定 payload | 真实 chat 消息 | probe 使用相似 payload |
| User-Agent | reqwest 默认 | opencode/version | probe 模拟相同 UA |
| 频率 | 错误后立即 + 密集 | 用户请求节奏 | probe 走独立低频率通道 |

**Probe 指纹对齐策略：**
- Probe 请求应复用 `ProviderAdapter.build_request` 逻辑，而非另起一套
- 不能因为没有 API key 就让 probe 走一条与真实流量完全不同的路径
- Probe 频率必须可控，不能因为 probe 本身的流量特征触发 WAF

## 2a. 429 分析与诊断

### 当前盲区

当前收到 429 后只记录状态码，不记录响应体。导致无法区分：

| 429 来源 | 响应体特征 | 应对策略 |
|---|---|---|
| Cloudflare WAF | HTML（JS challenge 或 CAPTCHA 页面） | 降低 IP 轮换频率，减少并发，粘滞路由 |
| 上游应用层 rate limit | JSON（`{"error":...}`） | 等待 retry-after，切换模型 |
| 代理节点限流 | JSON 或 HTML | 标记该节点，切换 route |

### v3.4 要求

```
POST /admin/events → 记录 429 时附带：
  - 响应体前 500 字节（区分 HTML vs JSON）
  - Content-Type 头
  - 出口 IP（exit_ip，需从上游响应或代理信息中提取）
  - retry_after 头（如有）
```

### exit_ip 捕获

当前 `RequestTelemetry.exit_ip` 和 `LedgerEvent` 中都声明了此字段，但**始终为 None**。

v3.4 中 `TransportAdapter` 增加：

```rust
trait TransportAdapter {
    // 已有方法
    async fn resolve_egress_ip(&self) -> Result<String, TransportError>;

    // 新增出口 IP 跟踪
    fn capture_egress_ip(&self, response: &reqwest::Response) -> Option<String>;
}
```

出口 IP 来源：
1. 上游响应头（如 `X-Forwarded-For`、`X-Real-IP` 等——需要 upstream 配合）
2. 代理服务商 API（如 WebShare 查询当前出口 IP）
3. 主动探测（通过专用探测请求获取 egress IP 并缓存）
4. 连接建立时从 SOCKS5 握手信息中提取（需底层支持）

## 4. 路由选择策略

### 基础策略

| 策略 | 说明 | 当前状态 |
|---|---|---|
| Healthy first | 只选健康 route | 部分：DispatchPool 评分含成功率 |
| Priority | 按优先级选最高 | ❌ 不存在 |
| Weighted round robin | 加权轮询 | 部分：加权评分轮盘赌 |
| Least latency | 最低延迟优先 | 部分：评分含延迟因子 |
| Least failure rate | 最低失败率优先 | 部分：评分含成功率 |
| Manual pinned | 手动固定 route | ❌ 不存在 |
| Free model preferred | 免费模型优先 | ❌ 不存在 |
| Sticky by client/model | 粘滞路由 | ❌ 不存在 |

### 当前 DispatchPool 评分（v3.0，可复用）

```rust
fn score(&self, idle_ms: u64) -> f64 {
    let base = 80.0;
    let success_factor = self.success_rate * 20.0;
    let idle_factor = ((idle_ms as f64) / 60_000.0).min(1.0) * 15.0;
    let latency_factor = if self.last_latency_ms < 5000.0 {
        10.0 * (1.0 - self.last_latency_ms / 5000.0)
    } else { 0.0 };
    let momentum = (self.success_count as f64).min(10.0) * 0.5;
    base + success_factor + idle_factor + latency_factor + momentum
}
```

## 5. 避免触发风控（WAF 规避策略）

### 背景

v3.0 429 根因分析结论：429 来自两个层面：
1. **Cloudflare WAF 层** — 100 个 WebShare SOCKS5 出口 IP 以**相同请求模式**（相同 model、相同 payload 结构、相同 user-agent、相同 header 布局、相同时间窗口）连续请求时，Cloudflare WAF 判定为爬虫/机器流量
2. **opencode 应用层** — 即使穿过 WAF，opencode 的 IP rate limiter（`ipRateLimiter.ts`）会按 IP 统计每日请求量，超限返回 `FreeUsageLimitError`

这是一个**架构设计问题而非代码 bug** — 使用大量 SOCKS5 轮换 IP 去请求 Cloudflare 保护的端点，必然会触发 WAF。

### opencode 限流源码证据

通过反编译 `sst/opencode` commit `b2baddcd`（当前生产环境基线版本）确认：

```typescript
// ipRateLimiter.ts — IP 限流器（实际源码，无 checkHeaders）
export function createRateLimiter(modelId, rateLimit, rawIp, request) {
  const limits = Subscription.getFreeLimits()
  const dailyLimit = rateLimit ?? limits.dailyRequests
  const isDefaultModel = !rateLimit
  
  // 终身计数器（仅默认模型） + 日计数器
  const lifetimeInterval = ""
  const dailyInterval = buildYYYYMMDD(now)
  
  _isNew = isDefaultModel && lifetimeCount < dailyLimit * 7
  
  if ((_isNew && dailyCount >= dailyLimit * 2) || (!_isNew && dailyCount >= dailyLimit))
    throw new FreeUsageLimitError("...", getRetryAfterDay(now))
}
```

**重要更正：** 当前生产版本（b2baddcd）**没有** `checkHeaders` 和 `dailyRequestsFallback` 逻辑。这是 `anomalyco/opencode` dev 分支后来增加的。当前版本中，opencode headers **不影响**限流额度，但发送仍有益处（指纹一致性 + 粘滞路由 + 未来兼容）。

关键发现：
- **限流按 IP**，每天 UTC 午夜重置（北京早 8 点），`retry-after` 是服务端本地计算
- **新 IP 有新手奖励**：前 `dailyLimit × 7` 次终身请求内额度翻倍
- **免费模型永远走 IP 限流**（`allowAnonymous = true`），给 API key 无用
- **日额度上限**：用完后返回 `FreeUsageLimitError`，retry-after 约 13 小时

### v3.4 规避策略

#### 5.1 请求指纹一致性

反直觉：**不是指纹越多越好，而是指纹要像真实客户端**。

| 原则 | 说明 |
|---|---|
| 每个 route 的请求指纹必须一致 | 不能 10 次请求用 10 种不同的 header 组合 |
| 指纹变化要有节奏 | 模拟真实浏览器的 header 更新频率 |
| Probe 指纹必须与真实请求对齐 | 当前 probe 不带 API key 是 bug |
| **建议发送 opencode 头** | 指纹一致性 + 粘滞路由 + 未来兼容（当前版本不影响额度） |

#### 5.2 IP 轮换策略

| 策略 | 适用场景 |
|---|---|
| 粘滞路由（Sticky By Client） | 同一客户端尽量固定出口 IP |
| 粘滞路由（Sticky By Model） | 同一模型的请求走固定 route + IP |
| 渐进切换 | 失败后只切换少数节点，而非全部轮换 |
| 降低并发 | 减少同一时刻打到同一 endpoint 的 IP 数量（从 100 降到 10-20） |

#### 5.3 请求模式多样化

- 不同 route 可配置不同的 User-Agent、header 布局
- 请求间隔加入随机抖动（当前 `smart_backoff` 已有基本抖动）
- 避免 100 个 IP 以相同 payload pattern 同时请求
- 每次重试不换节点（当前每次 retry 选新节点是 bug）——详见 [Phase 0.5 缺陷 4](../13_最优实施路线.md#缺陷-4每次重试选新节点加速池耗尽)

#### 5.4 探测隔离

Probe 请求本身不应触发 WAF：
- 走独立低频率通道（每分钟最多探测 3-5 个节点）
- **Probe 请求指纹需与真实请求对齐**（当前 probe 不带 API key 是 bug——详见 [Phase 0.5 缺陷 3](../13_最优实施路线.md#缺陷-3probe-不带-api-key)）
- 部分节点专门用于 probe，不承载真实流量

#### 5.5 落地措施

```rust
struct WafAvoidanceConfig {
    sticky_enabled: bool,
    sticky_ttl_secs: u64,
    max_concurrent_per_endpoint: u32,  // 建议 10-20
    probe_fingerprint_aligned: bool,
    request_jitter_ms: Range<u64>,
    user_agent_rotation: UaRotationStrategy,
}
```

### 关键差异：Clash Verge 为什么能用很久

| 维度 | Clash Verge（单 IP） | ZenProxyRS（100 IP 轮询） | 原因 |
|---|---|---|---|
| IP 数量 | 1 个固定 IP | 100 个 WebShare IP | WAF 判定爬虫 |
| 请求间隔 | 用户打字/思考的自然间隙 | 100 节点满并发 | 无自然节奏 |
| opencode 头 | CLI 自动发送 | 默认关闭 | 指纹不一致（当前不影响额度） |
| Probe 指纹 | 不适用 | 不带 API key | Probe 401 失败 |
| 重试行为 | 同一节点 | 每重试换新节点 | 加速池耗尽 |

## 7. 节点级数据录制（Pool-Drain 可观测性）

### 7.1 背景：池空事故暴露的数据缺口

当所有节点进入 RateLimited/Dead 池导致 503 时，查因会受阻于以下数据缺失：

| 诊断问题 | 卡在哪里 |
|---|---|
| 哪些节点先死？死的时间线？ | 全局 RingBuffer 无节点过滤，数据混杂 |
| 节点死前最后几笔请求是什么？ | 无 per-node 请求历史 |
| 429 响应体是 WAF HTML 还是 JSON？ | `error_body_summary` 恒为 None |
| 之前发生过同样的池空吗？ | WAL 未激活，重启后历史清零 |

### 7.2 新增数据结构

#### NodeRequestHistory（per-node 环缓冲）

```rust
// collector/node_history.rs
pub struct NodeRequestHistory {
    nodes: RwLock<HashMap<String, RingBuffer<HistoryEntry>>>,
    max_entries_per_node: usize,  // 默认 50
}

pub struct HistoryEntry {
    pub ts: i64,
    pub rid: String,
    pub model: String,
    pub status: u16,
    pub latency_ms: u64,
    pub was_rate_limited: bool,
    pub error_type: Option<String>,
    pub pool_from: Option<String>,
    pub pool_to: Option<String>,
}
```

**设计原则：** 不共享全局池。每个节点独立环缓冲，查节点 A 时不会被 B 的数据干扰。107 节点 × 50 条 × ~200 字节 ≈ 1MB 内存开销。

#### NodeLifetimeEvent（节点生命周期事件）

```rust
pub enum NodeLifetimeEvent {
    PoolTransition {
        ts: i64,
        node_id: String,
        from_pool: String,
        to_pool: String,
        reason: String,
        http_status: Option<u16>,
        request_id: Option<String>,
    },
    ProbeResult {
        ts: i64,
        node_id: String,
        ok: bool,
        latency_ms: u64,
        probe_kind: String,  // "error" | "ratelimited" | "periodic"
        error: Option<String>,
    },
    HealthChange {
        ts: i64,
        node_id: String,
        old_status: HealthStatus,
        new_status: HealthStatus,
        reason: String,
    },
}
```

### 7.3 数据流改造

```
proxy_with_retry
  │
  ├─ 成功/失败 → LedgerEvent（补全 error_body_summary + tokens + exit_ip）
  │
  ├─ DataCollector::record_request()
  │     ├─ 全局 RingBuffer
  │     ├─ RollingAggregator
  │     ├─ WAL append（当前未激活，需 Phase 1a 修复）
  │     └─ NodeRequestHistory.append() ← 新增 per-node 环缓冲
  │
  └─ PoolManagerImpl::report()
        └─ record_pool() → NodeLifetimeEvent ← 当前缺失，需修复
  
后台:
  └─ 每分钟 JSON 快照到文件（节点状态 + 池统计）
```

### 7.4 数据消费方式

| 接口 | 数据源 | 用途 |
|---|---|---|
| `/admin/nodes/{id}/history` | NodeRequestHistory | 查特定节点的最近请求序列 |
| `/admin/nodes/{id}/lifetime` | NodeLifetimeEvent | 节点在 5 个池之间的转移历史 |
