- 🔴 P0 — 数据准确性（必须修复，否则分析无意义）

- 🟢 P2 — 智能增强（锦上添花）

## 一、数据修复（修复已有字段的准确性）

### P0-01: 修复失败请求收录
- **当前问题：** `proxy_with_retry` 返回 `Err` 时完全不调用 `record_request`
- **影响：** Prometheus 计数只计成功；失败在仪表盘上不可见
- **方案：** 在 `proxy_handler` 层统一调用 `record_request`，无论成功/失败

### P0-02: 修复 `retry_count`
- **当前问题：** 始终为 0
- **方案：** 修改 `proxy_with_retry` 的返回类型，包含实际尝试次数

### P0-03: 修复 `rate_limited`
- **当前问题：** 始终为 false，收到 429 不标记
- **方案：** 从上游响应状态码推导

### P0-04: 修复 `upstream_ms`
- **当前问题：** 与 `latency_total_ms` 完全相等
- **方案：** 在 `proxy_with_retry` 内部单独计时（仅上游 HTTP 耗时，不含节点选择 + 重试）

### P0-05: 修复 `latency_total_ms`
- **当前问题：** 仅测量单次上游调用时间
- **方案：** 覆盖从请求到达 `proxy_handler` 到响应完成的完整路径（含调度 + 重试）

### P0-06: 修复 `prompt_tokens`
- **当前问题：** 始终为 0
- **方案：** 从上游返回的 `usage.prompt_tokens` JSON 字段解析（非流式场景）

### P0-07: 修复 `completion_tokens`
- **当前问题：** 始终为 0
- **方案：** 同上从 JSON 解析

### P0-08: 修复 `total_tokens`
- **当前问题：** 始终为 0
- **方案：** `total_tokens = prompt_tokens + completion_tokens` 或从 JSON 解析

### P1-09: 修复 `bytes_received`
- **当前问题：** 始终为 0
- **方案：** 在 `read_full_body` / 流式响应中记录实际接收字节数

### P1-10: 修复 `pool`
- **当前问题：** 始终为空字符串
- **方案：** 从 `DispatchResult` 中提取实际池名

## 二、新字段补充（增加高价值指标）

### P0-11: 实现 `ttft_ms`
- **当前：** 代码中始终为 `None` / 0
- **方案：** 在 `stream_to_axum` 中监听 Receiver 第一个 chunk，记录 `request_start` 到首 chunk 的耗时
- **价值：** 流式服务质量核心指标，区分"上游慢"和"首 Token 快但输出慢"

### P1-12: 实现 `exit_ip`
- **当前：** 始终为空字符串
- **方案：** 调用外部 IP 查询 API（如 `http://httpbin.org/ip`）获取节点出口 IP，缓存结果
- **价值：** IP 轮换可视化、地理分布分析

### P1-13: 添加 `error_code`
- **当前：** 无
- **方案：** 区分上游错误类型：timeout / connection_refused / dns_failure / bad_gateway
- **价值：** 快速定位根因，区分"代理问题"和"上游问题"

### P2-14: 添加 `cache_hit`
- **方案：** 为后续做语义缓存准备，标记是否命中缓存
- **价值：** 缓存命中率分析，判断缓存策略效率

### P2-15: 添加 `original_request_size`
- **方案：** 记录原始请求体大小（与 `bytes_sent` 对比可了解 patch 影响）
- **价值：** 理解模型 override / 修改对请求大小的影响

### P2-16: 添加 `socks5_handshake_ms`
- **方案：** 单独的 SOCKS5 代理握手耗时计时
- **价值：** 诊断代理性能瓶颈的关键

## 三、持久化 & 存储

### P0-17: 激活 WAL（Write-Ahead Log）
- **当前：** WAL 代码 95% 已完成（JSONL + gzip 压缩 + 轮转 + 24h 清理 + 启动恢复）
- **未激活原因：** `DefaultCollector::new()` 中 `wal: None`，`main.rs` 未传参
- **方案：** 
  1. Config 增加 `wal_path` / `wal_rotate_secs` / `wal_max_age_hours`
  2. `DefaultCollector::new()` 接受 `Option<WalConfig>` 参数
  3. `main.rs` 初始化时创建 WAL 实例传入
  4. `flush_snapshot` 后台任务中调用 WAL rotate

### P0-18: 激活 JSON Snapshot
- **当前：** `flush_snapshot` 调用 `state.collector.snapshot()` 但返回值被丢弃（`let _snap =`）
- **方案：** 将 snapshot 写入实际的 `JsonBackend`（已注册但未触发 write）

### P1-19: SQLite 持久化
- **方案：** 实现 `StorageBackend` trait + `rusqlite` 依赖
- **特性：** 按时间分片表，支持 `GET /admin/requests?since=&limit=` 历史查询
- **优势：** 结构化查询、无需外部依赖、嵌入式

### P2-20: 批量导出 CSV
- **方案：** 支持按时间段导出 telemetry 到 CSV 用于离线/BI 分析

## 附录A：节点故障排查标准流程（503 时使用）

```bash
# A1. 查 journald 真实失败原因
sudo journalctl -u zen-proxy-rs --no-pager -q | grep "proxy FAIL\|upstream request error" | tail -30
# -> 确认节点是被 429 / 502 / timeout / connection_refused 打死

# A2. 确认上游限额
curl https://opencode.ai/zen/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "x-api-key: public" \
  -d '{"model":"big-pickle","messages":[{"role":"user","content":"ping"}],"stream":false}'
# -> 429 = 上游 API Key 额度耗尽（非代理问题）
# -> 200 = 上游正常，问题在代理层

# A3. 确认 pool 恢复原因
sudo journalctl -u zen-proxy-rs --no-pager -q | grep -i "recover\|probe\|dead.*release\|ratelimited.*release"
# -> 看节点是自动冷却恢复还是重启清空状态
```
