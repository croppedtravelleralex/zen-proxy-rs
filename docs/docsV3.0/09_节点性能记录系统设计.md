# zen-proxy-rs 节点性能记录系统设计

> 目的：给每个 SOCKS5 节点打上最小开销的性能数据，故障时直接看 admin 端点，无需深查 journald

## 核心数据结构

### FailureKind（失败类型枚举）

```rust
#[repr(u8)]
pub enum FailureKind {
    Timeout            = 0,  // reqwest Err (connection timeout)
    ConnectionRefused  = 1,  // reqwest Err (connect refused)
    RateLimited429     = 2,  // HTTP 429
    BadGateway502      = 3,  // HTTP 502
    ServiceUnavailable503 = 4, // HTTP 503
    OriginError520     = 5,  // HTTP 520 (Cloudflare)
    DnsFailure         = 6,  // reqwest Err (dns)
    Other              = 7,  // catch-all
}
```

### NodePerfRecord（每个节点 64 字节，零堆分配）

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct NodePerfRecord {
    // 累计计数器
    pub success_count: u64,        // 请求成功次数（status < 400）
    pub fail_count: u64,           // 请求失败次数（status >= 400 或传输错误）
    pub total_latency_ms: f64,     // 延迟累计（用于算 avg）
    pub last_failure_at_ms: i64,   // 最后失败时间（epoch ms）
    pub last_success_at_ms: i64,   // 最后成功时间（epoch ms）
    pub last_failure_kind: u8,     // FailureKind 枚举值
    pub consecutive_failures: u32, // 连续失败次数
    pub count_429: u32,            // 429 累计
    pub count_5xx: u32,            // 5xx 累计（不含 429）
    pub total_bytes: u64,          // 流量累计（bytes_sent + bytes_received）
}
```

**衍生字段（读取时实时计算，不存储）：**
- `avg_latency_ms = total_latency_ms / (success_count + fail_count)`
- `error_rate = fail_count / (success_count + fail_count)`

## 存储策略

### 选型：内存 HashMap + 每 60s JSON 落盘

| 方案 | 结论 |
|------|------|
| **A) HashMap + JSON dump** | ✅ 推荐。与现有 RollingAggregator 模式一致，零新增依赖 |
| B) SQLite | ❌ 64 字节 × 100 节点 = 6.4KB 不值得引入 rusqlite |
| C) 挂 WAL | ❌ WAL 存的是按请求的 `RequestTelemetry`，按节点聚合需回放 |
| D) 纯内存 | ❌ 重启丢失历史数据 |

### NodePerformanceStore

```rust
pub struct NodePerformanceStore {
    inner: RwLock<HashMap<String, NodePerfRecord>>,
    snapshot_path: PathBuf,
}
```

**关键方法：**

| 方法 | 触发时机 |
|------|---------|
| `record(url, status, latency, bytes, failure_kind)` | 每次请求完成（`proxy_handler` 末尾） |
| `load_snapshot()` | 启动时从 `node_perf.json` 恢复 |
| `save_snapshot()` | 后台 flush 线程每 60s |
| `all()` / `get()` / `dead_nodes()` / `ratelimited_nodes()` | Admin 查询端点 |

### 接口设计

#### `record()` 内部逻辑

```
1. 查 HashMap: map.entry(node_url).or_default()
2. 判断 success/fail: status < 400 && failure_kind.is_none()
3. success → increment + reset consecutive_failures + 更新 last_success_at_ms
4. fail     → increment + update last_failure_kind + 更新 last_failure_at_ms
             if 429: count_429++
             if 5xx (non-429): count_5xx++
5. total_latency_ms += latency_ms
6. total_bytes += bytes_sent + bytes_received
```

## 性能开销

| 维度 | 数值 |
|------|------|
| 每个 `NodePerfRecord` | **64 字节** |
| HashMap 条目 + String key | ~72-136 字节 |
| 100 节点总计 | **~14-18 KB** |
| 每次更新时间 | **~100 ns**（HashMap lookup + RwLock write） |
| 占请求总耗时比例 | **<0.00002%**（上游调用 500~5000ms） |

## Admin API 端点

| 端点 | 响应 |
|------|------|
| `GET /admin/nodes` | 全部节点实时记录 |
| `GET /admin/nodes/{id}` | 单节点详情（id = urlencoded node_url） |
| `GET /admin/nodes/dead` | dead 节点 + 失败原因 + 进入 dead 时间 |
| `GET /admin/nodes/ratelimited` | ratelimited 节点 + 429 计数 |

## 代码集成点

### ProxyMeta 结构体

```rust
struct ProxyMeta {
    // 现有字段...
    pub failure_kind: Option<FailureKind>,  // 新增：传输层错误时设值
}
```

### proxy_handler 调用点

`proxy_with_retry` 返回后、`collector.record_request()` 之前：

```rust
let (resp, meta) = proxy_with_retry(...).await;

// 新增：节点性能记录
let latency_ms = meta.upstream_elapsed.as_millis() as f64;
state.node_perf.record(
    &meta.node_url,
    meta.status,
    latency_ms,
    body_bytes_len,
    meta.bytes_received,
    meta.failure_kind,
);

// 现有 telemetry
state.collector.record_request(&tele);
```

### 在 proxy_with_retry 内传 failure_kind

传输层错误（reqwest Err）时，`classify_reqwest_error()` 映射到 `FailureKind`，存入 `ProxyMeta.failure_kind`。HTTP 错误（502/503/429）由 `record()` 内部从 `status` 推导。

### 排查路径前后对比

```
之前: 503 → 翻 journald → 看节点状态 → 猜原因 → 超过15分钟
之后: 503 → curl /admin/nodes/dead → 直接看到失败原因和次数 → <5秒
```

## 启动恢复流程

```
1. NodePerformanceStore::new(path) → 创建空 HashMap
2. store.load_snapshot() → 从 node_perf.json 反序列化 (如文件存在)
3. 每 60s: store.save_snapshot() → 写入 node_perf.json (原子重命名)
4. 启动时如果文件不存在：空 HashMap 从零开始记录
```

重启后累计计数器保留（last_failure_at_ms、fail_count 等），可跨重启持续追踪。

## 使用场景

### 场景 1：1024 个节点中有 3 个挂了

```
curl -s http://localhost:4002/admin/nodes/dead
→ 看到 3 个节点，2 个 connection_refused，1 个 timeout
→ 直接在 SSH 中决策：换代理 or 等自动冷却
```

### 场景 2：100 个节点全部

```
curl -s http://localhost:4002/admin/nodes | jq '[.nodes[] | select(.error_rate > 0.1)] | length'
→ 错误率 >10% 的节点数
```

### 场景 3：长时间运行后检查

```
curl -s http://localhost:4002/admin/nodes | jq '[.nodes[] | {success: .success_count, fail: .fail_count, latency: .avg_latency_ms}] | sort_by(.fail) | reverse[:5]'
→ 失败最多的 top 5 节点
```
