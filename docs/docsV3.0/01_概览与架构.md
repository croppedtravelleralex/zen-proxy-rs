## 一、功能总览

### 1.1 架构模式总纲

```
榫卯耦合架构的核心原则：
─────────────────────────

① 每个模块分两层：
   ┌─ 接口层 (trait)   — 对外暴露「能做什么」，写在文档前半部分
   └─ 实现层 (impl)    — 内部紧密耦合，怎么写都行
                           
   示例：
   trait PoolManager {
       fn dispatch(&self, req: &RequestMeta) -> Result<DispatchResult, DispatchError>;
       fn report(&self, node_id: NodeId, result: ResultKind, latency_us: u64);
   }

   struct PoolManagerImpl<D, A, R, K, C> { ... }  // 内部任意紧耦合
   impl<P: Pool> PoolManager for PoolManagerImpl<P> { ... }

② 所有模块间的通信走 trait，不走 struct 字段
   禁止：proxy.rs 直接调 state.token_bucket.allow()
   允许：proxy.rs 调 pool_manager.dispatch()（通过 trait 方法）

③ 每个 trait 只做一件事，且接口数 ≤ 5
   trait Pool {
       fn acquire(&self) -> Option<NodeRef>;
       fn release(&self, node, result);
       fn available(&self) -> usize;
       fn name(&self) -> &str;
   }

④ 换实现不用换调用方
   换提供商 -> 改 main.rs 的类型参数 + nodes.json
   换调度算法 -> 加一个 impl Scheduler 的结构体
   换探活策略 -> 加一个 impl ProbeScheduler 的结构体

⑤ 模块内紧、模块间松
   ┌─────────────┐     trait      ┌─────────────┐
   │ PoolManager  │ ──────────->   │  proxy.rs   │
   │ (实现可任意  │    接口       │ (不认具体   │
   │  紧耦合)     │ ←──────────   │  类型，只认 │
   │              │    回调       │  接口)      │
   └─────────────┘               └─────────────┘
```

### 2.4 架构模式对比

| 维度 | 旧版(v1) | 现在(v2, 紧耦合) | **新版(v3, 榫卯耦合)** |
|------|---------|-----------------|----------------------|
| 模块间通信 | 用函数名裸调，跨模块操内部对象 | 通过 AppState 上帝对象，proxy 直接调 6 个模块 | **通过 trait 接口，模块间不认具体类型** |
| 替换提供商 | — | 改 4~5 个文件 | **改 1 行类型参数 + 1 个 JSON** |
| 新增一个池 | — | 动 6 个文件 | **加 1 个文件实现 trait** |
| 运行时开销 | — | 0 | **0（编译期展开）** |
| 可测试性 | — | 差（要 mock 整个 AppState） | **好（各池可独立测）** |
| 二进制 | — | Debug 86MB, 不敢切 Release | **Release <10MB, 稳定运行** |
| 数据采集 | — | 6个原子计数器散落在 metrics.rs | **统一 DataCollector，5层指标收口** |

### 3.1 PoolManager

```rust
// ── 接口层 ──

/// 池管理器榫头：proxy.rs 只认这个，不认具体实现
pub trait PoolManager: Send + Sync {
    /// 为请求调度一个节点
    fn dispatch(&self, req: &RequestMeta) -> Result<DispatchResult, DispatchError>;
    /// 汇报请求结果
    fn report(&self, node_id: NodeId, result: ResultKind, latency_us: u64);
    /// 当前各池统计
    fn pool_stats(&self) -> PoolStats;
}

pub type NodeId = String;

pub struct NodeRef {
    pub id: NodeId,
    pub url: String,
}

pub struct PoolStats {
    pub dispatch_size: usize,
    pub active_size: usize,
    pub ratelimited_size: usize,
    pub dead_size: usize,
    pub pool_transitions: usize,
    pub active_concurrency: usize,
}

pub struct DispatchResult {
    pub node: NodeRef,
    pub client: reqwest::Client,
}

pub enum DispatchError {
    NoResource,          // 调度池为空 -> -999
}

pub enum ResultKind {
    Success,             // 200
    RateLimited,         // 429
    Error { kind: ErrorKind },
}
```


### 3.2 Pool (各池通用接口)

```rust
// ── 通用池接口 ──

pub trait Pool: Send + Sync {
    /// 关联的节点 ID 类型
    type NodeId: Clone + Hash + Eq;
    /// 从池中取出一个节点
    fn acquire(&self) -> Option<NodeRef<Self::NodeId>>;
    /// 回收一个节点（汇报结果）
    fn release(&self, node_id: &Self::NodeId, result: &ResultKind);
    /// 从池中移除节点
    fn remove(&self, node_id: &Self::NodeId);
    /// 向池中添加节点
    fn add(&self, node: NodeRef<Self::NodeId>);
    /// 池中当前可用节点数
    fn available(&self) -> usize;
    /// 池名称（日志/监控）
    fn name(&self) -> &'static str;
}
```

#### 3.2.1 DispatchPool（调度池）

```rust
// ── 接口层 ──
// 继承通用 Pool，无额外接口

// ── 实现层 ──
pub struct DispatchPool<N: NodeProvider> {
    nodes: Vec<PoolNode<N>>,
}

struct PoolNode<N> {
    node: Arc<N>,
    base_score: AtomicU64,          // 健康度 0~100 (f64 bits)
    consecutive_successes: AtomicU32,
    recent_results: VecDeque<bool>, // 最近20次结果，环形缓冲
    avg_latency_ms: AtomicU64,      // (f64 bits)
    idle_since: AtomicU64,          // 最后释放时间
}

// 核心调度算法：
//   final_score = base_score × 0.50
//               + success_rate × 0.20
//               + idle_factor × 0.15
//               + latency_factor × 0.10
//               + momentum × 0.05
//   加权随机选取（分数越高概率越大，但不绝对）
```

## 九、性能推演

### 在 panda (2C4G, 30Mbps) 上的预测

```
瓶颈分析：
  CPU:    2 核，新版每秒可处理 ~2000 万次原子操作
  带宽:   30Mbps ≈ 3.75MB/s ≈ 375 次普通请求/秒
  内存:   4GB，新版 release <10MB，远小于 Python 的 391MB

瓶颈是带宽，不是 CPU。

新旧版性能对比：
                              旧版(debug,86MB)    新版(release,<10MB)
  单请求 CPU 开销              0.001%              0.001% (一样)
  HTTP 请求耗时               1.5~6s             1.5~6s (一样)
  每秒可处理请求数              ~375               ~375 (带宽上限)
  内存占用                     86MB               <10MB
  节点重试浪费的带宽            高(漏接黑名单)       低(429池+死池隔离)
  限流畅开销                  无(TokenBucket关闭)  低(max_concurrent动态调)

结论：榫卯架构在 panda 上不会变慢，但会减少带宽浪费、提升稳定性。
```
