## 一、性能推演

### 1.1 瓶颈分析

```
panda 配置:
  CPU:  2 核 Intel Xeon (Skylake, ~2.5GHz)
  RAM:  4GB
  NET:  30Mbps (3.75MB/s)

瓶颈是带宽，不是 CPU。
30Mbps 下每秒最多 ~375 次普通请求（每次 ~10KB）。
新版榫卯架构的 CPU 开销与紧耦合几乎一致（差 0%）。

三个架构在 panda 上的实际差异:

                     CPU 消耗       内存            HTTP 延迟      带宽浪费
旧版 (紧耦合, debug)  <1% (闲置)    86MB          1.5~6s          高（无黑名单）
新版 (榫卯, release)  <1% (闲置)    <10MB         1.5~6s          低（429池+死池）

差距:                 不可感知        8.6x           完全一样        天壤之别
```

### 1.2 各操作延迟预算

```
操作                              延迟              占 30Mbps 带宽
────                              ────              ────────────
一次 HTTP 请求 (端到端)            1.5~6s            100% (串行)
SOCKS5 建连 (新节点)              200~500ms         0.5%
node_probe 每 30s 全探活 100 节点  约 5s             0.1%
429池探活 (每 2~4h, 3~5 节点)     约 3s             可忽略
死池探活 (每天 8点, 全部节点)      约 10s            可忽略
```

### 1.3 请求吞吐量估算

```
               旧版(Python)    旧版(Rust debug)   新版(Rust release)
────           ───────────    ───────────────    ─────────────────
单核 RPM       937             >10,000            >10,000
2核 RPM        1,874           >20,000            >20,000
30Mbps 上限    22,500          22,500              22,500
实际瓶颈       Python GIL      带宽                带宽

结论: 在 panda 上，三种实现都到不了 22,500 RPM 的带宽上限。
      Rust 比 Python 快 10 倍以上，但都被 30Mbps 带宽卡住。
      好在 Rust 省内存 (10MB vs 391MB)，可以省下资源做其他事。
```

## 二、部署方案

### 2.1 部署架构

```
                           WSL (开发/测试)
                           ┌──────────────────┐
                           │  zen-proxy-rs    │
                           │  :14000          │
                           │  -> WebShare      │
                           └──────────────────┘

                           panda (生产)
                           ┌──────────────────┐
                           │  zen-proxy-rs    │
                           │  systemd 服务     │
                           │  :4000            │
                           │  -> WebShare      │
                           └──────────────────┘
```

### 2.2 systemd 服务

```ini
[Unit]
Description=Zen-Proxy-RS (榫卯架构)
After=network.target

[Service]
Type=simple
User=root
WorkingDirectory=/opt/zen-proxy-rs
ExecStart=/opt/zen-proxy-rs/zen-proxy-rs
Restart=always
RestartSec=5
Environment=RUST_LOG=info
Environment=PORT=4000
Environment=UPSTREAM_BASE=https://opencode.ai/zen
Environment=NODES_FILE=/opt/zen-proxy-rs/nodes.json

[Install]
WantedBy=multi-user.target
```

### 2.3 环境变量 (配置项)

| 变量 | 默认值 | 说明 |
|------|--------|------|
| `PORT` | `4000` | HTTP 监听端口 |
| `BIND_ADDRESS` | `0.0.0.0` | 绑定地址 |
| `UPSTREAM_BASE` | `https://opencode.ai/zen` | 上游 API 地址 |
| `NODES_FILE` | `nodes.json` | 节点列表文件路径 |
| `ALLOW_DIRECT_FALLBACK` | `false` | 是否允许直连 fallback |
| `CONNECT_TIMEOUT_SECS` | `5` | SOCKS5 连接超时 |
| `REQUEST_TIMEOUT_SECS` | `120` | 上游请求超时 |
| `POOL_MAX_RETRIES` | `3` | 失败重试次数 |
| `ADMIN_API_KEY` | `""` | 管理 API 密钥 |
| `WARM_INTERVAL_SECS` | `10` | 预热池间隔 |
| `PROBE_BATCH_SIZE` | `5` | 每轮探活数 |
| `RUST_LOG` | `info` | 日志级别 |

## 三、实施计划

### Phase 1 — 代码重构 (3天)

```
Day 1: trait 定义 + 池模块拆分
  ├── 写 pool/mod.rs (trait Pool, trait PoolManager)
  ├── 写 pool/manager.rs (PoolManagerImpl 状态机)
  ├── 写 pool/dispatch.rs (加权随机 + node_provider + session_cache)
  ├── 写 pool/active.rs (引用计数 + max_concurrent)
  ├── 写 pool/ratelimited.rs (429隔离 + 探活)
  └── 写 pool/dead.rs (连续失败 + 恢复)

Day 2: proxy 改造 + collector + provider
  ├── 写 collector/ (DataCollector trait + DefaultCollector + 后端)
  ├── 写 provider/ (NodeProvider trait + WebShare 实现)
  ├── 改 proxy.rs (去掉 state.xxx 调用, 改为 trait 调用)
  ├── 删旧文件 (token_bucket, selector, pool, node_probe 等)
  └── 改 main.rs + server.rs + config.rs

Day 3: 编译 + 测试
  ├── cargo build --release
  ├── 单元测试 (各池独立可测)
  ├── 集成测试 (走完整链路)
  ├── cargo clippy + cargo fmt
  └── cargo deny check
```

### Phase 2 — 灰度上线 (1天)

```
Step 1: WSL 内部测试
  └── 替换 /home/lenovo/zen-proxy-rs/target/release/zen-proxy-rs
  └── 测试各池流转 (dispatch -> active -> ratelimited -> dead -> 恢复)
  └── 测试 -999 "没有资源可用"
  └── 测试 /admin/fuse 熔断

Step 2: panda 生产上线
  └── scp zen-proxy-rs -> /opt/zen-proxy-rs/
  └── systemd 服务配置
  └── 停止旧 Python proxy.py
  └── 启动新 Rust 服务
  └── 验证 /health /metrics /v1/models

Step 3: NewAPI 切换
  └── NewAPI 上新建通道指向 panda:14000
  └── 逐步切流量，观察指标
  └── 观察 429 率变化、各池状态
```

### Phase 3 — 持续改善

```
└── 监控告警 (池空、熔断、大量429)
└── CI/CD (GitHub Actions -> 自动构建 -> scp)
└── 容器化 (Dockerfile -> Docker Compose)
└── 更多节点提供商 (BrightData, 自家代理池)
```

## 四、回滚方案

```
如果新版出现问题：

  ① NewAPI 切回旧通道（指向旧 Python proxy.py :4000）
  ② systemctl stop zen-proxy-rs
  ③ systemctl start zen-proxy-py   (旧 Python 版)
  ④ 问题排查

  从问题出现到全部切回旧版：< 5 分钟
```

## 五、关键指标

### 上线后关注的指标

| 指标 | 健康值 | 告警阈值 | 说明 |
|------|--------|---------|------|
| 调度池大小 | 50~100 | < 10 | 可用节点数 |
| 429池大小 | < 20 | > 50 | 当日被限流的节点数 |
| 死池大小 | 0 | > 5 | 连续失败节点 |
| 请求成功率 | > 95% | < 80% | 上游响应正常比例 |
| 请求 429 率 | < 10% | > 30% | 上游限流比例 |
| 调度池空次数 | 0 | > 1 | 返回 -999 的次数 |
| RPM | 根据业务基线 | 超过基线 3 倍 | 每分钟请求数 |
| P95 延迟 | < 5s | > 10s | 请求延迟 95 分位 |
| 带宽使用率 | < 80% | > 90% | 30Mbps 上限 |
| 熔断状态 | off | on | 管理员误操作时告警 |

## 六、附录

### 6.1 架构演进路线

```
v1.0 (Python)         ->  紧耦合, 9进程, 391MB
  │
v2.0 (Rust, 当前)     ->  紧耦合, 1进程, 86MB (debug)
  │                     功能等价, 大量死代码
  │                     无接口抽象, 上帝对象 AppState
  │
v3.0 (Rust, 目标)     ->  榫卯耦合, 1进程, <10MB (release)
                         接口+实现分离, 泛型组装
                         六池状态机, 统一数据采集
```

### 6.2 名词对照表

| 中文 | English | 说明 |
|------|---------|------|
| 榫卯耦合 | Mortise-Tenon Coupling | 接口层(trait) + 实现层(impl) 分离 |
| 调度池 | Dispatch Pool | 加权随机选节点的池 |
| 使用池 | Active Pool | 正在处理请求的节点池 |
| 429池 | RateLimited Pool | 被上游限流的隔离池 |
| 探活期 | Probe Period | 非429失败后的探测期 |
| 死池 | Dead Pool | 连续失败的不可用节点池 |
| 数据采集器 | Data Collector | 统一收口5层指标 |
| 节点提供商 | Node Provider | 抽象代理来源 |
| 加权随机 | Weighted Random | 按分数高低概率选人 |
